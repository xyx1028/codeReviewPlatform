# 需求开发评审一致性平台 V1.54：MCP统一镜像发布最终执行方案

## 1. 背景与目标

公司流水线的统一镜像目前只包含 Web 与 Worker，Linux `release.sh` 也只更新这两种应用容器。用户希望以后一次发布同时拉取并启动远程 MCP 服务，不再手工运行独立 Node 进程。

## 2. 范围与非目标

包含：将 MCP 源码与锁定依赖打进现有公司应用镜像；在既有 `crp-selfhost-net` 上以独立容器运行 MCP；发布脚本预检配置、拉取镜像、更新 MCP 并检查健康；更新 Linux 安装步骤和发布 Skill。

不包含：数据库迁移或 Edge Function 业务改动、自动生成账号密码和访问凭证、自动申请证书或修改 Nginx 站点、在 CI 节点直接部署 Linux。

## 3. 当前实现与问题

`Dockerfile.workercompany` 的复制列表没有 `mcp/code-review-mcp`。`deploy/supabase-selfhost/scripts/release.sh` 只处理迁移/Functions、Worker 和 Web。MCP 虽已有独立的 Node 入口、健康端点、systemd 示例，但当前 Linux 没有启动 MCP。

## 4. 需求与验收标准

1. 新的公司镜像包含 MCP 入口及锁定依赖，仍能分别运行 Worker 和 Web。旧流水线产物没有 MCP 入口，首次发布必须等待新镜像构建。
2. Linux 的独立 MCP Compose 只加入已有 `crp-selfhost-net`，监听端口只绑定宿主机 `127.0.0.1`，凭证由未入库的 env 文件注入。
3. `release.sh --dry-run` 在改动服务前检测 MCP 配置存在和 Compose 可渲染；`--apply` 拉取同一镜像并启动 MCP，健康端点返回预期标识才记录发布完成。
4. MCP 配置缺失、容器启动失败或健康失败时脚本明确报错，不宣称成功。已执行的迁移或其他容器更新不会自动回滚。Linux 上旧 systemd 服务若监听同一端口，必须先核对并停用。
5. 用户可按顺序在 Linux 创建配置、预览、正式发布并查看 MCP 状态；现有 4 个 Worker、Web 与数据库数据不因本改动被清除。

## 5. 总体设计

同一 `CRP_APP_IMAGE` 分别作为 Worker、Web 和 MCP 的镜像；Compose 为每种角色指定独立启动命令。发布流程为 GitLab release 同步 → 预检本地配置 → 迁移/Functions → 拉取应用镜像 → Worker 排空更新 → Web 更新 → MCP 更新及健康检查 → 写成功记录。

## 6. 数据与接口设计

不涉及数据库、RPC、RLS、Storage 和 Edge Function。MCP 沿用现有 `/mcp` 与 `/healthz` 接口，新增 Linux 部署配置文件路径，不新增业务接口。

## 7. 前端与 Worker/运行时改造

前端和 Worker 业务逻辑不变。公司 Dockerfile 在构建期安装 MCP 的锁定依赖并复制入口源码。MCP 容器使用现有 Supabase 网络名访问内部 API，以独立环境文件获取平台账号和调用方访问凭证。

## 8. 安全、兼容与回滚

MCP 凭证只在 Linux 本地 `.docker/mcp.selfhost.env` 中，文件被 Git 忽略，镜像不包含它；对宿主机只暴露回环地址的端口。Compose 强制启用 Bearer 校验，固定监听 `0.0.0.0:8848`（容器内部）和内部 Supabase URL，防止误配匿名模式或宿主机 localhost。既有 systemd 示例不自动启用，避免双进程争用 8848。发布失败不删库、不删卷。可使用上次成功的应用镜像重新发布容器，但数据库迁移不能随镜像自动回滚。Nginx /mcp 对外入口需人工按公司网络和证书现状配置；脚本只验本机端口。

## 9. 实施步骤与文件范围

1. 更新 `Dockerfile.workercompany` 复制 MCP 并安装其依赖。
2. 新增 MCP Compose 和不含秘密的环境模板，扩展 `release.sh` 预检、拉取、启动、健康检查。
3. 更新 `deploy/supabase-selfhost/README.md`、`mcp/code-review-mcp/README.md` 和 `.codex/skills/crp-linux-release/`，给出首次配置及以后发布步骤。
4. 同步 `src/lib/product-version.ts` 到 V1.54；执行 Shell、Compose、MCP、Worker、前端和镜像验证。

## 10. 验证结果

- `bash -n deploy/supabase-selfhost/scripts/release.sh`、Compose 配置校验、`git diff --check` 通过。
- MCP 包原有 67 项测试通过；Compose 安全边界、实际发布预检（含引号凭证、不输出秘密、缺少访问凭证）与 Worker 发布配置测试合计 10 项通过。
- 公司 Dockerfile 本地构建成功，生成 `linux/amd64` 镜像；从该镜像按 MCP Compose 启动的容器 Healthy，宿主机 `127.0.0.1:8848/healthz` 返回 HTTP 200 和 `codereview-mcp` 标识，测试容器已停止并删除。Mac 为 arm64，构建使用公司 amd64 基础镜像，因此出现架构提示，不影响构建或本次仿真。
- 新镜像连接指定的本地 Supabase 启动一个隔离的 Worker，入口预先创建 DRAIN，确认 `worker_started` 和 `worker_drain_complete`；未领取业务任务，测试容器已停止并自动删除。
- `npm run worker:typecheck`、`npm run worker:build`、`npm run web:typecheck`、`npm run build` 和版本一致性校验通过。Worker 全量测试首次有 1 项受默认 5 秒超时影响；使用 `--testTimeout=10000` 复跑后 63 文件、1093 项通过，14 文件、35 项跳过。
- 未执行公司 Linux 的真实发布、账号配置、Nginx 对外转发或 MCP 提交真实评审；这些依赖用户在目标机器填写专用账号和访问凭证、提交 release 并等待 CI 产出新镜像。
