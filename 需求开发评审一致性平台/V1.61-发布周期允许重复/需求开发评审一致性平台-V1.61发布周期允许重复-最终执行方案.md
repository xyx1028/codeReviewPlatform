# 需求开发评审一致性平台 V1.61：发布周期允许重复最终执行方案

## 1. 背景与目标

`review_batch.week_code`（页面上的「发布周期」）从 `0001_review_platform.sql` 起就是
`not null unique`。这条唯一性在产品上不成立：**同一个发布周期下本来就可能有多个批次** ——
按模块拆、按代码基线拆（同一周期既评 `feature_dev` 又评 `release`）、或者重跑一次评审。
唯一约束把这些正常用法挡在"创建批次"那一步。

它在两个地方直接伤到使用者：

- **页面**：`src/App.tsx` 的表单校验直接报「发布周期已存在，请换一个」—— 用户被迫改一个
  与事实不符的日期，只为绕过约束。
- **远程 MCP**：为了不撞唯一键，MCP 给自动生成的发布周期加了时分秒和随机后缀
  （`20261019-MCP174949-20be86`）。结果在批次列表的「发布周期」那一列里，它和旁边人工批次的
  `20261016` 完全不是一类值，既难读也无法比对。

目标：去掉唯一性，让同一发布周期下可以有多个批次；同时把为规避该约束而生出的复杂度
（候补编码、唯一键冲突重试、相应的错误文案）一并删掉。

## 2. 范围与非目标

本次包含：

- 数据库：删除 `review_batch` 上 `week_code` 的唯一约束（及随之消失的唯一索引），
  补一个**非唯一**索引；
- 前端：去掉创建批次表单里的「发布周期已存在」校验；
- MCP：发布周期固定用干净的 8 位 `YYYYMMDD`，删除候补编码与唯一键冲突重试；
- 删除 MCP 侧"发布周期相撞，请重试"的错误文案（该错误不再可能出现）。

明确不包含：

- **不放开 `not null`。** 发布周期在页面上是必填项，这一点没有变化。
- **不改发布周期的格式与年份范围。** MCP 的 `release_cycle` 仍校验 8 位、真实日期、
  年份在当前年前 2 后 3（与页面下拉一致）——放开的只是"能不能重复"。
- 不改批次的其它唯一性：主键 `id` 不变，批次身份仍然各自独立。
- 不涉及 Edge Function、Worker 与能力契约。

**没有任何逻辑依赖这条唯一性。** 已全仓检索确认：

- 迁移/RPC 里除了建表那一行，`week_code` 只出现在 `0015_operation_log_audit.sql` 的
  `batch_week_code_snapshot`（删除批次时留存的快照副本，与唯一性无关）；
- 没有 `on conflict (week_code)`、没有按 `week_code` 单行查询的 RPC；
- 批次列表 RPC（`0021_review_batch_creator.sql`）按 `created_at desc` 排序，不涉及 week_code。

## 5. 总体设计

单点改动，没有新组件：

```text
数据库   drop constraint review_batch_week_code_key
         create index idx_review_batch_week_code（非唯一）
   ↓
前端     去掉表单里的"发布周期已存在"校验
   ↓
MCP      week_code = release_cycle ?? 当天 YYYYMMDD   （一次插入，不再重试）
```

非唯一索引是顺手补的：这次放开之后，"同一发布周期下有哪些批次"会成为一种自然查法，
而原来的唯一索引随约束一起消失了，留一个比将来再加便宜。

## 6. 数据与接口设计

- **数据库**：`supabase/migrations/20261020045257_allow_duplicate_week_code.sql`
  - 用 `do $$ ... $$` 按"唯一且只约束 week_code 一列"查出约束名再 drop，而不是写死名字
    （名字是建表时隐式生成的，若某环境手工重建过可能叫别的）；
  - 再 `drop constraint if exists review_batch_week_code_key` 兜一次，语义更直白；
  - `create index if not exists idx_review_batch_week_code`；
  - 更新列注释。
- **RPC / RLS / 触发器**：不涉及，一行未改。
- **Edge Function**：不涉及。
- **能力契约**：不涉及。
- **环境变量**：无新增。

## 7. 前端与 Worker/运行时改造

前端：`src/App.tsx` 一处校验移除，并把表单说明改成「同一周期可以有多个批次」。
页面结构、组件、路由不变。

Worker：**不涉及**，无需重建镜像。Worker 从不写 `week_code`，也不按它查询。

MCP：`review.mjs` 删去 `buildWeekCodeFallbacks` / `isWeekCodeConflict` /
`insertBatchWithWeekCode`，建批次回到一次普通 insert；`format.mjs` 删去相撞文案。

## 8. 安全、兼容与回滚

- **纯放宽，不涉及数据删除。** 删约束不动任何行；既有批次、在途导入单、历史分析任务
  全部不受影响。
- **旧数据天然兼容**：原来每个 week_code 都唯一，放开后仍然合法。
- **新旧 Worker 可混跑**：Worker 不参与 week_code 的写入与校验。
- **回滚**：本仓库禁止 destructive down migration。若将来要恢复唯一性，需另写一个前进的
  迁移，并且**必须先处理掉届时已存在的重复值** —— 直接加约束会失败。这一点已写进迁移注释。
- **环境边界**：本次只在**本地两个库**应用并验证（`supabase_db_codeReviewPlatform` 与
  selfhost 的 `supabase-db`）。**云端未应用**，`supabase db push` 由用户执行。
