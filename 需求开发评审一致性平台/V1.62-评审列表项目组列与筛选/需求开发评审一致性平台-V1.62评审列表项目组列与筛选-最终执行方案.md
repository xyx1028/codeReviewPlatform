# 需求开发评审一致性平台 V1.62：评审列表项目组列与筛选最终执行方案

## 1. 背景与目标

评审列表（`/batches`）能看到发布周期、状态、代码基线、模型、创建人、创建时间，
但看不到这批需求**来自哪个项目组**。而项目组恰恰是最常用的筛选维度 —— 一个人通常只关心
自己组的评审，现在只能靠「评审描述」里的自由文本去猜。

目标：列表新增「项目组」列，并支持按项目组筛选（含多选与"未关联"）。

## 2. 范围与非目标

本次包含：

- 列表 RPC `list_review_batches_with_creator()` 新增 `workspace_names text[]`；
- 前端列表新增「项目组」列（多项目组用多个标签展示）与列筛选（可搜索、多选）；
- 聚合用索引 `idx_review_story_batch_workspace`。

明确不包含：

- **不给 `review_batch` 加项目组列。** 项目组是由批次**里面的需求**决定的，冗余存储要在
  导入、重试、删除需求等每条路径上维护一致性，而它只服务一个展示列。批次是人工创建的
  量级（几十到几百），列表里聚合的成本可以忽略。
- **不给历史批次补项目组。** Excel 时代导入的需求 `linky_workspace_name` 为 null
  （实测本地库那个 26 条需求的批次就是这样），如实留空，不编造。
- 不改批次详情页、不改 Linky 看板、不改 MCP、不改 Worker。

## 3. 当前实现与问题

```text
0021_review_batch_creator.sql
  list_review_batches_with_creator() → 13 列，没有项目组

src/App.tsx 的批次表格
  评审描述 | 发布周期 | 状态 | 代码基线 | 模型 | 创建人 | 创建时间 | 操作
                                  ↑ 没有项目组，也没有任何按组筛选的入口
```

项目组的数据其实一直都在，只是没被取出来。实测本地库（2026-10-20）：

| 批次 | 需求数 | `review_story.linky_workspace_name` | 最近导入单的 `workspace_name` |
|---|---|---|---|
| 20260901 | 1 | 平台开发组 | 平台开发组 |
| 20260903 / 18 / 19 / 24 | 3/2/2/5 | 工具开发组 | 工具开发组 |
| 20260923 | 26 | （全为 null） | （无导入单） |

最后一行是 Excel 时代的历史批次 —— 它说明"项目组"这一列必须允许为空。

另外注意 `BatchWorkspace` 这个既有类型**不是**项目组：它是"批次工作集"
（batch + stories + results），名字容易误导，本次没有复用它。

## 5. 总体设计

```text
review_story.linky_workspace_name  ──┐
   （Worker 在内网取数时冻结）        │  coalesce 两级回退
                                      ├──► list_review_batches_with_creator()
linky_batch_import_request            │        .workspace_names text[]
   .workspace_name  ─────────────────┘              │
   （批次为空时的来源）                              ▼
                                        前端：标签展示 + 列筛选（包含判定）
```

两级来源的顺序是刻意的：**已冻结的需求是事实**，所以优先；批次为空时才退到"本来要导入
哪个组"。后者尤其有用 —— 一个导入失败的空批次能显示出它的目标项目组，否则列表上只是
一个没有任何线索的空行。

返回 `text[]` 而不是拼好的字符串：拼了就没法按单个项目组精确过滤。

## 6. 数据与接口设计

- **迁移**：`supabase/migrations/20261020052658_batch_list_workspace_names.sql`
  - **必须 `drop function` 后重建**：`create or replace` 改不了 `RETURNS TABLE` 的列集合；
  - 重新 `revoke`/`grant`（drop 会连带丢掉授权）；
  - `create index if not exists idx_review_story_batch_workspace on review_story (batch_id, linky_workspace_name)`。
- **类型**：`ReviewBatchListItem` 增加 `workspace_names: string[]`。
- **前端纯逻辑**（新增，便于单测）：`src/components/batches/workspace-column.ts`
  - `normalizeWorkspaceNames`：去空白/空值/重复 + 中文排序；
  - `buildWorkspaceFilters`：汇总筛选项，仅在存在空项目组批次时追加「未关联项目组」；
  - `matchesWorkspaceFilter`：**包含**判定。
- **RLS / 触发器 / Edge Function / Worker / 能力契约**：均不涉及。

## 7. 前端与 Worker/运行时改造

前端 `src/App.tsx`：在「发布周期」之后插入「项目组」列，宽 168、`ellipsis`，
多项目组渲染为多个 `Tag`（鼠标悬停显示完整列表），无项目组显示次要色 `-`；
`filters` 由当前列表数据构造，`filterSearch` 开启，`onFilter` 用包含判定。

Worker：**不涉及**，无需重建镜像。

## 8. 安全、兼容与回滚

- **只读增强**：新增的是一个输出列和一个索引，没有任何写路径变化。
- **权限不变**：RPC 仍是 `security definer` + 仅 `authenticated` 可执行，且只暴露
  项目组名称（已经通过需求列表对登录用户可见的信息），不新增任何数据暴露面。
- **drop function 的风险点**：drop 会丢授权，所以迁移里紧跟 `revoke`/`grant`，
  并由 SQL 测试断言两者（E7）。另断言不留旧重载（E6）—— 留一个 13 列的旧重载会让
  前端随机拿到没有项目组的那一版。
- **旧前端 + 新 RPC**：多一个字段不影响旧前端解析。
- **新前端 + 旧 RPC**：`workspace_names` 为 `undefined`，`normalizeWorkspaceNames` 当作
  空数组处理，列显示 `-`，不会崩 —— 已由前端单测覆盖。
- **回滚**：另写一个前进迁移恢复 13 列版本即可（无数据后果）。
- **环境边界**：只在**本地两个库**应用并验证；**云端未应用**，`supabase db push` 由用户执行。

### 10.4 前端筛选逻辑（E10~E12）

10 条单测全部通过。其中两条是过程中真实踩到的点：

- **拼音序不是码点序**：`zh-CN` 下 `gong(工) < ling(灵) < qian(前)`，我最初把期望值写成了
  "前、工、灵"而实现是对的。测试里已注明，避免后来者把实现"改回"码点序。
- **多项目组必须用包含判定**：写成相等的话，跨组批次在任何单组筛选下都会消失。
