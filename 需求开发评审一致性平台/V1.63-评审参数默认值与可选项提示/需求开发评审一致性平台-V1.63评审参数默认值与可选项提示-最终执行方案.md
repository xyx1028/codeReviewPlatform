# 需求开发评审一致性平台 V1.63：评审参数默认值与可选项提示最终执行方案

## 1. 背景与目标

用户在客户端里只说一句"帮我评审 US-2026-042380"时，模型还得先问清两件他未必在意的事：
代码基线和提交时间窗口。因为这两个参数此前是**必填且没有默认值**的。

目标：给它们默认值（`release` + 14 天），让一句话就能拿到确认卡片；同时在卡片上**摊开**
这两个值用了默认、以及还能选什么，由用户确认或直接说改成什么。

这一版改掉了一条此前刻意反着做的决定。原来的理由是：这两个参数直接改变评审结论，
**静默替人选一个默认值比报错更糟**。那条理由没有被推翻 —— 它被换了一种方式满足：
**默认值绝不沉默**。使用者在花钱之前就看到"用的是默认值"和"还能选什么"，于是"确认"
是一次真正的选择，而不是对一个他不知道存在的选项的默认接受。

## 2. 范围与非目标

本次包含：

- `branch` 与 `commit_window_days` 从必填改为**可选**，缺失时套用默认值；
- 默认值可配置：`CRP_DEFAULT_BRANCH`、`CRP_DEFAULT_COMMIT_WINDOW_DAYS`，配错即启动失败；
- 确认卡片标出 `← 默认值`，并列出**全部替代项**（分支带人话含义，窗口列出其余取值）；
- 卡片明确告诉模型"用户要改就带着指定值重新调一次"；
- `describe_submit_options` 同步标明默认值；
- 修正一处措辞：项目组未填写时不再显示「你给的是「（未填）」」。

明确不包含：

- **不放开 `story_code`**：它没有合理默认值。
- **不放开模型选择**：仍由服务端 `CRP_DEFAULT_MODEL` 决定。
- **不弱化确认门禁**：默认值只是让第一步更容易到达，第二步仍必须带令牌；
  参数变了旧令牌照旧失效。
- 不改数据库、Edge Function、Worker、前端页面。

## 3. 当前实现与问题

```text
start_requirement_review
  required: ['story_code', 'branch', 'commit_window_days']
                            ↑ 这两个没有默认值

用户：帮我评审 US-2026-042380
模型：（必须先问）要评哪条分支？看多少天的提交？
用户：（往往并不在意，只想要个合理默认）
```

实测截图里模型自己绕出了一个变通：它在回复里手写"请确认评审参数，例如回复：确认，
feature_sit，14天"并列出可选值。也就是说**这个需求是真实的**，只是此前靠模型即兴发挥，
而工具描述约束不了模型的实际行为 —— 不同客户端、不同模型给出的提示会不一样，
也可能根本不提示。所以它该是服务端的固定行为。

## 5. 总体设计

```text
args（branch/window 可缺）
   │
   ▼
resolveSubmitParams(args)        ← 两个入口共用（lookup 与 submit）
   │  · 缺失 → config.defaults.* → 模块常量
   │  · 同时记下 branchIsDefault / windowIsDefault
   ▼
确认卡片：标「← 默认值」+ 列全部替代项 + 提示"要改就重新调一次"
   │
   ▼
令牌签入**解析后**的值 → 第二步按令牌里的值提交
```

两个入口共用一个解析函数是必须的：如果查询与提交各自套默认，第一步签进令牌的值和
第二步算出来的"期望值"就可能不一致，于是刚确认过的提交会被自己的门禁拒掉。

## 6. 数据与接口设计

- **数据库 / Edge Function / 能力契约**：均不涉及。

新增环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `CRP_DEFAULT_BRANCH` | `release` | 必须是三个受支持分支之一，否则启动失败 |
| `CRP_DEFAULT_COMMIT_WINDOW_DAYS` | `14` | 必须是 7/14/21/28 之一，否则启动失败 |

工具契约变化：

```text
start_requirement_review
  required: ['story_code', 'branch', 'commit_window_days']
→ required: ['story_code']
  branch             可选，默认 release
  commit_window_days 可选，默认 14
```

**可选不等于不校验**：给了非法值仍被 V1.59 的 schema 门禁拒（`branch: 'main'` 照旧报错）。

## 7. 前端与 Worker/运行时改造

**均不涉及。** 只改 `mcp/code-review-mcp/**`。

一处实现细节值得记下：`BRANCH_LABELS` 在 `format.mjs` 与 `query-tools.mjs` 各有一份
（避免 format ↔ query-tools 的循环依赖，后者已依赖 review → config）。两份同值由
`confirmation-defaults.test.mjs` 的一条测试断言，改一份忘了另一份会失败。

## 8. 安全、兼容与回滚

- **确认门禁没有被弱化。** 默认值只影响"第一步更容易到达"；第二步仍必须带令牌，
  令牌仍绑定四个关键参数，参数变了仍然失效（F10 覆盖）。
- **不会把默认值悄悄变成既成事实**：卡片标注 + 替代项列举 + "要改就重新调"三件事
  各有一条测试守着（F4/F6/F7/F8）。少任何一件，默认值就退化成"替你偷偷决定"。
- **兼容**：老客户端继续传 branch/window 完全不受影响（显式值优先，且不标默认）。
- **回滚**：MCP 是独立进程，回滚 = 用旧镜像重启；也可只把两个环境变量改掉而不回滚代码
  （但无法恢复"必填"语义，那需要回滚代码）。

## 10. 验证结果

### 10.1 真实接口：用户只说一句话（F1/F3/F4/F6/F7/F8）

对 `https://linky.kingdee.com` 真实调用 `start_requirement_review({ story_code: 'US-2026-042380' })`：

```text

将要评审的需求：
  需求编号：US-2026-042380
  需求名称：【智能体实例】【console】创建智能体实例界面优化
  所属项目组：工具开发组
  当前状态：需求编写完成
  迭代：202610-2（1019-1023）
  发布窗口：R20261106
  关联特性：【智能体】【console】企业自建的智能体支持禁用 (FT-2026-002463)
  需求负责人：张烨   开发负责人：李俊豪   测试负责人：王麒达
  需求正文：560 字；附件：0 个

本次评审参数：
  代码基线（目标分支）：release —— 发布分支（最接近线上）  ← 默认值
  提交时间窗口：14 天  ← 默认值
  项目组（提交时实际使用）：工具开发组

也可以换成其它取值（告诉我就行，不改就按上面的提交）：
  代码基线还可以选：

  · workspace_name：已自动填为「工具开发组」。你没有指定项目组，已按需求编号反查到的实际项目组填入。

确认无误后，用下面这个令牌再调用一次 start_requirement_review 即可提交
```

### 10.2 用户改参数的路径（F5/F10/F11）

| 场景 | 结果 |
|---|---|
| 指定 `feature_sit` + 21 天 | 卡片显示这两个值，**不**标默认；替代项里出现 `release` 与 14 天 |
| 只指定 `feature_dev` | 分支不标默认，窗口仍标 `14 天 ← 默认值` |
| 带**旧**令牌 + 改成 `feature_dev` 提交 | 被拒：`CONFIRMATION_PARAM_MISMATCH`，且未建批次 |

### 10.3 配置校验（F2/F12）

```text
CRP_DEFAULT_BRANCH=feature_sit / CRP_DEFAULT_COMMIT_WINDOW_DAYS=21  → 生效
CRP_DEFAULT_BRANCH=main        → 启动失败：CRP_DEFAULT_BRANCH 只能是 feature_dev / feature_sit / release
CRP_DEFAULT_COMMIT_WINDOW_DAYS=30 → 启动失败：只能是 7 / 14 / 21 / 28
配置里缺这两项 → 退到模块常量 release/14，参数段不出现「（空）」
```

F12 这条是实现过程中真实踩到的：最初 `resolveSubmitParams` 只读 `config.defaults.*`，
手工构造的配置缺这两项时会产出 `undefined`，卡片上显示成「（空）」，直到 `assertBranch`
才报错 —— 一个本可以在源头消失的失败。现在退到模块常量。
