# 需求开发评审一致性平台 V1.52：Worker默认并发配置最终执行方案

## 1. 背景与目标
统一发布固定缩至 1 个 Worker，旧的 Linux 环境文件将每个 Worker 并发限制为 1。用户要求后续发布自动保持 4 个副本、每副本 2 条需求任务并发。

## 2. 范围与非目标
更新公司 Linux 发布脚本、公司 Compose 覆盖层、配置示例和发布验收；不改变本地通用 Compose 的副本默认，不调整模型并发限额，不新增数据库迁移。不把任务并发解释为系统线程数。

## 3. 当前实现
release.sh 调用 worker-drain-restart.sh --scale 1；verify_worker 只检查第一个容器。worker.selfhost.env 示例为 WORKER_STORY_CONCURRENCY=1。

## 4. 验收标准
每次统一发布排空全部旧副本后启动 4 个；每个容器有效 WORKER_STORY_CONCURRENCY=2，即使旧 env 文件仍为 1 也生效；全部 4 个副本都有 worker_started 且配置为 2 才报告发布成功。dry-run 仅输出目标容量，不更新服务。

## 5. 总体设计
release.sh 默认副本数 4；公司专用 worker.override.yml 在 environment 中明确设为字符串 2，优先于 env_file，不改写含密钥的文件。原有 drain 仍等待全部旧副本完成任务，再使用同一覆盖层重建。显式把本轮选定的 CRP_APP_IMAGE 传给 drain 子进程，避免继承终端里过期的镜像值。发布验收有界等待最多 30 轮。

## 6. 数据与接口
不涉及数据库、API、RPC 或新 CLI 参数；并发参数复用现有 WORKER_STORY_CONCURRENCY。

## 7. 前端与运行时
前端仅同步产品版本。最大需求并发为 4×2=8，模型配置的并发上限、任务可用性和系统资源仍可进一步限制实际吞吐。

## 8. 安全兼容与回滚
不变更 Docker 网络；仍只加入 crp-selfhost-net。不改写旧 env 密钥。回滚时同时还原副本数和公司覆盖层的并发设置，再通过 drain 重建。

## 9. 实施文件
release.sh、worker.override.yml、env/worker.selfhost.env.example、README.md、脚本回归测试、src/lib/product-version.ts；既有 V1.51 文档的发布说明同步指向新策略。

- 已完成默认 4 副本、公司覆盖层并发 2、全部副本启动检查和明确镜像参数传递。示例环境文件及 README 同步更新。
- 新增 7 项发布回归全部通过：4×2 正常、仅 3 个副本、第 4 个尚未启动、旧并发 1、无副本、真实 Docker Compose 配置合并（旧 env 为 1 仍解析为 2 且网络不变）、drain 收到本次镜像及 --scale 4（终端旧镜像不影响）。
- `bash -n`、`git diff --check`、`worker:typecheck`、`worker:build`、`web:typecheck`、`build`、`lint` 均通过。构建和 lint 保留既有 chunk 体积与 11 条告警。
- Worker 全量回归 1092 passed、35 skipped；跳过用例为既有可选集成测试，未视为通过。

## 11. 用户手动发布
与 V1.51 ZIP 兼容改造一起检查并提交推送 release，流水线构建成功后，在 Linux 先 git pull，再执行现有 release.sh --dry-run、--apply。正式发布会排空现有副本，自动启动 4 个且每个并发为 2，之后不再额外手动扩容。
