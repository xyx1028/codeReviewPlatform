# 需求开发评审一致性平台 V1.22：技能 AI 优化一次写对最终执行方案

> 状态：**已实现并在本地验证通过**（2026-09-24）。云端推送与云端 Worker 更新由使用者手动执行，见第 10 节末尾的发布清单。

## 1. 背景与目标

### 背景（先说清线上到底发生了什么）

同一个技能连续失败两次，错误码都是 `SKILL_OPTIMIZATION_MODEL_OUTPUT_INVALID`，但**根因是两个不同的问题**。查云端 `skill_ai_optimization_request` 的真实终态：

| 时间 | `error_message` | `model_attempts` | 真实根因 |
|---|---|---|---|
| 09:42 | `the model changed nothing` | 3 | 证据为空，模型按提示词要求没改 |
| 10:14 | `the model output contains no JSON object` | 3 | **输出被 token 上限截断** |

两次页面上显示的都是同一句罐头文案（「路径不合规、放错目录、frontmatter 的 name 被改、文件或整包超出容量上限之类」），一条都没命中。

#### 根因 A：证据为空却放行（09:42 那次）

1. **入队门禁口径错**。`admin_enqueue_skill_ai_optimization` 数的是
   `count(distinct job_id) from analysis_job_skill_snapshot`，即"这个技能被冻结进过几个 Job"。
   而技能被冻结进 Job 发生在作业创建阶段，与那个 Job 是否产出过评审结论无关。
   截图里的技能：被 1 个分析任务引用过，**0 条评审结论**，verdict 分布全 0、抽样为空 —— 门禁放行。
2. **提示词要求模型别改**。系统提示词第 9 条：「不要编造证据里没有的业务事实；证据不足时宁可少改」。
   模型拿到一份全 0 的统计，照规则办事，返回空的 `files`。
3. **解析器把"没改"判成"写错了"**。`files` 与 `deletedFiles` 都为空时
   `reject('the model changed nothing')` → 回灌原因让模型重写 → 证据还是那份全 0 的统计 →
   同样的答案 → 3 次用尽，终态失败。

#### 根因 B：输出被截断，平台看不见（10:14 那次）

| 事实 | 值 |
|---|---|
| 三个启用的模型配置 `max_output_tokens` | 全部 **8192** |
| Worker 发出去的 `max_tokens` | 硬编码 **60000** |
| 失败技能的包 | `SKILL.md` 6826 字节 + 7 份 references（每份 3~5 KB），展开 39 KB |
| 每次调用耗时 | 约 76 秒（10:14:12 → 10:18:01 跑了 3 次） |

协议要求模型把改过的文件**整篇回写**成 JSON 字符串。它同时改两三份资料就超过 8192 token，
端点按自己的上限截断，正文停在字符串中间、连一个 `}` 都没有 —— `extractJsonObject` 于是报
"输出里没有 JSON 对象"。平台**完全看不见**这件事，因为响应里的 `finish_reason` 从来没被读过。

外加一条让诊断变难的实现：`describeOptimizationError` 对已登记的错误码**丢掉** `error_message`，
只显示罐头文案。于是真实原因躺在数据库里，管理员看到的是四条与事实无关的猜测。

### 目标

- AI 按技能包的结构规范**一次写对**，而不是靠"写错再回灌重写"收敛；
- 输出量与**改动量**成正比，而不是与文件大小成正比 —— 8192 的输出上限下也能改一份 6.8 KB 的 `SKILL.md`；
- 没有可学习的评审证据时**不进入模型阶段**，而不是烧三次模型调用再失败；
- 模型判断"不该改"是一条**合法终态**，不再伪装成结构错误；
- 失败原因如实显示给管理员，截断有自己的错误码。

## 2. 范围与非目标

### 本次包含

- 入队与执行两侧的证据门禁改为"有评审结论"，两个证据函数输出 `review_result_count`；
- **锚点编辑协议（`edits`）**：改现有文件只写要改的那几段，输出量与改动量成正比；
- **模型输出上限随请求冻结**（`max_output_tokens_snapshot`），Worker 按模型真实上限发 `max_tokens`，并把预算写进提示词；
- **截断被识别**：读 `finish_reason`，独立错误码 `MODEL_OUTPUT_TRUNCATED`，并作为可修的重试（回灌"改用 edits 缩小输出"）；
- 提示词改造：目录/扩展名表由校验器常量生成、frontmatter 原文行、容量现状、输出样例、自检清单；
- 新增终态码 `SKILL_OPTIMIZATION_NO_CHANGE_NEEDED`（模型明确判断不需要改），不重试、不产草稿；
- 前端：按钮可用性判据同步收紧、错误文案带上服务端原文、"不需要改"不再显示成失败、截断有自己的文案；
- SQL 测试、Worker 单测、前端单测、文档。

### 明确不包含

- **不改结构校验规则本身**。`validateSkillArchive` 是最终闸门，一个字没动 —— 锚点编辑的结果
  会被当成"该文件的新全文"走**同一条**校验通路。
- **不放宽 fail-closed**。路径、角色/扩展名、frontmatter、容量、UTF-8、图片 magic 全部照旧拒；
  锚点不唯一时平台绝不替模型猜改哪一处。
- **不改 dsh 运行时、能力契约或 manifest**。
- **不做流式输出 / 分片续写**。一次调用一份完整 JSON，这条不变。

## 5. 总体设计

```mermaid
flowchart TD
  A[点 AI 优化] --> B{有评审结论?}
  B -- 没有 --> C[NO_EVIDENCE 立即拒绝\n不建请求行、不调模型]
  B -- 有 --> D[入队 → Worker claim]
  D --> E{Worker 二次确认结论数}
  E -- 0 --> F[NO_EVIDENCE 终态\nmodelAttempts=0]
  E -- >0 --> G[提示词：规范契约 + 证据 + 自检清单]
  G --> H[模型]
  H -- 给出改动 --> I[fail-closed 解析 → 重新打包 → validateSkillArchive]
  H -- noChangeNeeded --> J[NO_CHANGE_NEEDED 终态\n不重试、不产草稿]
  I -- 不合规 --> K[回灌原因重写，最多 3 次]
  I -- 通过 --> L[走人工上传同一条链路产出草稿]
```

保留重试机制，但它从"主要收敛手段"降级成"兜底"：规范现在写在提示词里。

## 6. 数据与接口设计

迁移 1：`supabase/migrations/20260924095026_skill_ai_optimization_require_review_results.sql`，
三个 `create or replace`，签名全不变，无表结构变化：

| 对象 | 变化 |
|---|---|
| `admin_get_skill_review_evidence(uuid)` | 输出加 `review_result_count` |
| `get_skill_review_evidence_for_optimization(uuid, text, uuid)` | 输出加 `review_result_count` |
| `admin_enqueue_skill_ai_optimization(uuid)` | 门禁从"有引用"改为"有 ≥1 条 `ai_review_result`"，口径与证据函数的 `evidence` CTE 逐字一致 |

迁移 2：`supabase/migrations/20260924102123_skill_ai_optimization_output_budget.sql`：

| 对象 | 变化 |
|---|---|
| `skill_ai_optimization_request` | 加列 `max_output_tokens_snapshot integer`（null = 升级前的历史行） |
| `admin_enqueue_skill_ai_optimization(uuid)` | 入队时写入 `ai_model_config.max_output_tokens` |
| `claim_next_skill_ai_optimization_task(text)` | 返回体加 `max_output_tokens_snapshot` |

Worker / 前端类型：`SkillReviewEvidenceSnapshot.review_result_count?: number`、
`SkillReviewEvidence.review_result_count?: number`、
`SkillAiOptimizationClaim.max_output_tokens_snapshot?: number | null`（可选 = 兼容未升级的后端）。

新错误码：`SKILL_OPTIMIZATION_NO_CHANGE_NEEDED`、`MODEL_OUTPUT_TRUNCATED`。状态仍沿用 `FAILED`，
不新增状态枚举 —— 前端按错误码把它们渲染成 warning / 专属文案，避免改数据库枚举与既有查询。

模型输出协议（V1.22b）：

```json
{
  "summary": "…",
  "edits": [{ "path": "SKILL.md", "find": "<原文里唯一出现的片段>", "replace": "<新文本>" }],
  "files": { "references/new.md": "<新建文件全文>" },
  "deletedFiles": []
}
```

`edits` 的应用规则（全部 fail closed）：路径必须是已存在的**文本**文件；`find` 必须在当前正文里
**恰好出现一次**（0 次或多次都拒，绝不猜第一处）；`replace` 可以是空串（删掉这一段）；同一文件
多个 edits 按顺序叠加；同一路径不能同时出现在 `edits` 和 `files`。应用结果被当作"该文件的新全文"，
之后与整篇回写走**同一条**校验通路（容量、frontmatter、UTF-8、未改动检测）。

## 8. 安全、兼容与回滚

- **没有放宽任何校验**。`validateSkillArchive` 仍是最终闸门；脚本仍然只能在 `scripts/` 下、
  仍然触发 `contains_scripts` 与发布页额外确认；图片仍然只能删。
- **`noChangeNeeded` 不能被用来绕过什么**：它的唯一效果是"本次不产出草稿"。
- **门禁收紧的代价**：只被引用、还没产出结论的技能现在**不能**发起优化。这是有意的 ——
  那种状态下优化没有任何输入。页面会说清是"没被引用过"还是"引用过但还没有结论"。
- **旧数据/未升级后端**：`review_result_count` 缺席时两端都回退到结论分布求和，口径一致，
  因此数据库与 Worker/前端可以分别发布，顺序不敏感。
- **已存在的失败行不受影响**：历史 `FAILED` 行照旧显示，只是文案里会多出服务端原文。
- **已知缺口（本次不修）**：平台无法判断模型回写的文件正文是否被**截断**。
  提示词明确要求"完整全文、不许省略号占位"，但如果模型在输出中途被 token 上限截断，
  JSON 会解析失败（可发现）；若它主动写了个更短但语法完整的版本，则会作为正常改动进入草稿 ——
  这就是"必须人工看 diff 再发布"这条产品约束存在的理由。
- **回滚**：写一个新迁移把三个函数覆盖回 20260924050153 的版本（禁止编辑既有迁移），
  Worker 与前端回滚上一版。三者可独立回滚。
