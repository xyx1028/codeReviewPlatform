# 需求开发评审一致性平台 V1.48：内网自部署Supabase最终执行方案

> 交付对象：负责公司 Linux 服务器部署与验证的同事。
> 本版目标：直接部署到公司的 Linux 服务器，提供公司网络内可访问的平台与远程 MCP。
> 状态：**仓库侧已完成**（MCP 提交状态不确定缺陷已修复并有测试；部署模板、反向代理、
> systemd、备份/恢复/自检脚本、selfhost 构建与启动入口已落地并在本机验证）。
> **服务器侧未开始**：尚未连接公司服务器、未部署、未初始化数据库、未切换配置。
> 逐条状态见第 10 节。2026-10-14。

## 1. 背景与目标

公网 Supabase Cloud 因流量额度超限返回 402。用户已有公司 Linux 服务器，希望本版直接在该服务器自部署 Supabase、前端、Worker 和远程 MCP，供公司同事使用。

本版不经过“Mac 临时承载”阶段。历史业务数据、账号、评审批次、结果及附件不需要迁移；在 Linux 上新建空环境并初始化所需配置。

目标是复用当前代码完成内网部署，不重写评审引擎或改成其他数据库。

## 2. 范围与非目标

### 本次包含

- 官方 Docker Compose 自部署 Supabase，以及独立 PostgreSQL、Auth、Storage、RPC/RLS、Vault、Edge Runtime。
- 前端静态站点、现有后台 Functions、1 个初始 Worker、远程 MCP。
- 新账号、模型密钥、必要业务配置、内网地址与 HTTPS、备份和全链路验收。
- 公司同事通过浏览器访问平台，通过 Qoder/Codex 等客户端连接 MCP。

### 本次不包含

- 历史数据导入；旧公网库和 Mac 本地测试数据的删除或重置。
- 后端技术栈重写、业务表重设计、评审 Agent/Harness 逻辑重构。
- 公司 SSO、微信登录、公网开放、穿透和高可用集群。首轮使用平台邮箱账号。
- 新消息队列或调度系统。先通过配置降低空闲轮询频率。

## 3. 当前实现与改动判断

当前项目依赖：

| 能力 | 当前入口 | 本版做法 |
|---|---|---|
| 登录、会话、账号 | `src/lib/supabase.ts`、`src/lib/api.ts` | 使用自部署 Auth 和新账号 |
| 数据、任务、权限 | `supabase/migrations/`、大量 RPC/RLS | 在新库执行既有迁移，保留业务逻辑 |
| 模型密钥 | `admin-model-config` + Vault | 在新环境部署函数，重新配置密钥 |
| 文件与技能 | Storage、`skill-bundle-admin` | 新建存储，部署现有函数，重新上传所需技能 |
| 后台评审 | `worker/src/index.ts`、`worker/src/db/client.ts` | 构建 Linux 镜像，切换 URL/key/网络参数 |
| 远程提交 | `mcp/code-review-mcp/` | 配置服务端账号、内网平台地址，常驻运行 |

**工作量判断：以部署、初始化和运行配置为主；现有业务代码大部分复用。不能承诺零代码修改，也不是只替换一个 Supabase URL。**

明确区分：

1. 必做的部署工作：Compose、内网网络/域名/证书、密钥、Functions 文件与依赖、静态服务、运行管理、备份脚本。
2. 按验收结果决定的少量适配：Functions 的依赖加载/JWT 兼容、签名文件 URL 的外部地址、MCP 环境变量加载及 Linux 启动方式。
3. 已知独立缺陷：MCP 在提交响应不确定时不能盲目删批次或声称没有任务。**已修复**（见第 10.1 节），
   在提供给同事使用前的这一项不再阻塞。
4. 不必为部署重写：需求导入、代码准备、分析流程、数据库业务 RPC、评审结果展示、Harness 工具与运行策略。

已确认旧公网 4 个 Worker 停止。本机开发栈与公网配置保持原样；公司服务器尚未检查，部署人员须补齐主机信息及连通性。

## 4. 验收标准

1. 公司同事能用内网 HTTPS 地址登录平台并调用 MCP，无须依赖用户的 Mac。
2. 新 Supabase、前端、Functions、Worker、MCP 常驻；重启服务器后能够恢复服务。
3. 新库初始化完整，Auth、RLS、Vault、RPC、Storage 正常；普通账号不能越权。
4. 模型管理、文件上传下载、技能发布和评审页面可用。
5. MCP 受理指定一条公司需求后立即返回受理编号与平台链接，不等待评审完成。
6. Linux Worker 能访问 Linky、GitLab、模型，完成真实需求导入、代码快照、Agent 评审、结果和证据落库。
7. 浏览器和客户端配置不含服务端 key、模型密钥、数据库密码；对外链接不含 localhost 或 Docker 内部主机名。
8. Worker 初期 1 副本，轮询 15 秒；所有数据请求连接内网 Supabase，不恢复旧公网轮询。
9. 数据、文件、配置及必要运行卷有备份，并完成一次恢复验证。

## 5. 总体设计

初期一台 Linux 服务器，使用 Docker Compose，不引入 Kubernetes。建议逻辑分层：

- HTTPS 反向代理：转发前端、Supabase API 和 MCP。
- Supabase：官方固定版本，数据与配置保存在服务器持久目录。
- 前端：Nginx 提供构建后的 `dist/`，支持 SPA 路由回退。
- Worker：复用现有镜像构建，接入 Supabase Docker 网络，初期 1 副本。
- MCP：独立 Node 常驻进程或容器，有访问令牌鉴权。

示例域名（占位，必须换成公司实际可解析、证书覆盖的域名）：

| 用途 | 公司用户访问地址 | 服务端内部地址 |
|---|---|---|
| 平台 | `https://review.corp.example` | 前端静态服务 |
| Supabase | `https://supabase.corp.example` | `http://crp-supabase-api:8000` |
| MCP | `https://mcp.corp.example/mcp` | MCP 进程/容器 |
| Studio | Supabase 管理入口，限部署人员 | 保持独立管理员鉴权 |

流向：公司浏览器/MCP → Linux 内网 Supabase → 任务队列 → Linux Worker → Linky/GitLab/模型 → 内网 Supabase → 平台展示。

建议目录：

```text
/srv/crp/
  app/                 # 本项目代码
  supabase-source/     # 锁定的官方 Supabase 源文件
  supabase/            # 正式 Compose、.env、functions 与 volumes
  backups/             # 备份暂存，另复制到独立备份位置
```

部署目录由公司部署账号管理。秘密和数据位于服务器，不提交到 Git；可复用模板放在项目 `deploy/supabase-selfhost/`，只包含占位值。

## 6. 数据与接口设计

无新业务表或 RPC。使用 `supabase/migrations/` 初始化新空环境，保留当前数据模型、函数、触发器、RLS 与 Storage bucket。

先确认 PostgreSQL 17、`pgcrypto`、`supabase_vault`、Auth/Storage 系统 schema 和数据库角色兼容。检查迁移内的规则及仓库白名单是否符合公司部署环境。

使用显式目标连接串初始化，禁止默认操作仓库原来的 linked 云端项目。**本机演练已跑通，下面是
实际可用的命令**（两处细节是实测踩出来的，照抄旧写法会失败）：

```bash
# 在 /srv/crp/app 执行。
# 1) 密码必须**百分号编码**：生成的 POSTGRES_PASSWORD 含非字母数字字符，
#    CLI 的 --db-url 要求 percent-encoded，否则连接串被截断成另一个地址。
# 2) 必须显式 sslmode=disable：CLI 默认要求 TLS，自部署 pooler 不支持，
#    报 "tls error (The server does not support SSL connections)"。
PGPW='<.env 里的 POSTGRES_PASSWORD>'
ENC=$(node -e "process.stdout.write(encodeURIComponent(process.argv[1]))" "$PGPW")
export INTERNAL_DB_URL="postgresql://postgres.crp-selfhost:${ENC}@127.0.0.1:54342/postgres?sslmode=disable"

supabase db push --db-url "$INTERNAL_DB_URL" --dry-run
supabase db push --db-url "$INTERNAL_DB_URL"
```

用户名是 `postgres.<POOLER_TENANT_ID>`，端口是 `docker-compose.crp.yml` 把 supavisor 收到回环的
`54342`（session 模式）。`--skip-vault` 在本仓库不需要（`config.toml` 里没有 vault secrets 声明），
加了也无害。

实测结果（本机演练，公司服务器需复跑）：108 个迁移全部应用成功，PostgreSQL **17.6**，
`pgcrypto` 与 `supabase_vault` 就位，public schema 67 张表 / 298 个函数 / 44 条 RLS 策略 /
4 个私有 Storage bucket。§6 原先"先确认兼容性"那一条据此可以勾掉。

不使用 `--include-seed`，不执行 `db reset`。`supabase/seed.sql` 是本地测试种子，不能复制其测试账号到正式环境。兼容错误不得通过改历史迁移解决；需要补迁移时遵守仓库迁移命名 Skill 并验证。

手动运维可把 `deploy/supabase-selfhost/scripts/apply-migrations.sh` 固定放在公司 Linux 的
`/home/kduser/crp/apply-migrations.sh`。每次运行在临时目录拉取 GitLab `release` 的 `supabase/`，
完成或失败后清理临时检出，不维护常驻的代码仓库。用临时内存凭据缓存复用 GitLab 登录；使用本机 `.env` 中的密码生成显式
`127.0.0.1:54342` 连接串，先 dry-run，确认后用 `--apply` 执行 `db push`。
它每次从 `supabase_migrations.schema_migrations` 判断待执行文件，已执行的会跳过；如果历史
与文件不一致则停止并人工排查，不自动 repair。迁移成功后同步变更的 Edge Functions 目录、
重启容器并验证两个必需函数加载；加载失败时恢复旧 Function 文件，数据库迁移不自动回滚。
脚本未在公司 Linux 实跑，首次执行仍需核对目标、预览清单、外部依赖可用性及迁移结果。

通过 Auth API 创建管理员、普通用户和 MCP 专用 REVIEWER 账号，使用新随机密码；模型、凭据和需要的 Skill 重新初始化。不导入旧 Vault 密文。

`DISABLE_SIGNUP=true` 时自助注册会被拒（实测 422），预置账号用 service-role 走
`POST /auth/v1/admin/users`（带 `"email_confirm": true`），再由第一个账号调平台的
`claim_initial_admin` 升为 ADMIN。触发器会给新账号建 `user_profile`，默认角色 REVIEWER ——
MCP 专用账号用这个默认角色就够（`can_create_review_batch()` 允许 ADMIN/REVIEWER）。

## 7. 各服务部署与配置

### 7.1 前端

在构建机创建 `.env.selfhost.local`：

```dotenv
VITE_SUPABASE_URL=https://supabase.corp.example
VITE_SUPABASE_ANON_KEY=<新实例客户端 anon key>
```

执行 `npm run build -- --mode selfhost`，将 `dist/` 部署到静态服务。Nginx 使用 `try_files $uri $uri/ /index.html`，确保批次详情深链接可直接打开。

Vite 配置是在构建时写入产物的：更换域名/key 后必须重新构建，不能只改运行服务器上的 `.env`。

### 7.2 Worker

创建独立的 `.docker/worker.selfhost.env`：

```dotenv
SUPABASE_URL=http://crp-supabase-api:8000
SUPABASE_SERVICE_ROLE_KEY=<新实例服务端 key>
POLL_INTERVAL_MS=15000
WORKER_STORY_CONCURRENCY=1
```

Worker 通过共享 Docker 网络访问 API 网关，无须依赖 `host.docker.internal`。Linux 不应照搬 Mac 的 Docker Desktop 主机访问配置。

从 `.docker/worker.env.example` 填写 GitLab 与 Linky 相关参数。若 Linux 主机和容器均能直连公司接口，使用 `LINKY_NETWORK_ACCESS_MODE=DIRECT`，模型配置也选择实际可用的直连模式；若确需代理，使用公司可达代理并确认容器访问，不复用 Mac 的代理地址。

在目标 Linux 上构建或拉取与服务器 CPU 架构匹配的 Worker 镜像；不要假设 Mac 上已构建的镜像存在于 Linux。保留会话、代码缓存、任务与技能缓存的 named volumes。

既有任务租约和心跳参数保持合法组合。本版先通过 1 副本/15 秒轮询降低空转；自动空闲退避及 402 熔断可另行修复，不重写调度系统。

### 7.3 MCP

创建专用服务端配置，填写新实例地址、anon key、新 REVIEWER 账号、默认模型和令牌；`CRP_PLATFORM_WEB_URL` 必须为公司可访问的前端地址。

- 若 MCP 部署为容器并接入共享网络，数据库 API 地址使用 `http://crp-supabase-api:8000`。
- 若 MCP 作为 Linux systemd 进程运行，使用服务器回环网关 `http://127.0.0.1:54341` 或可访问的内网 HTTPS 地址。
- 反向代理把公司 MCP 域名的 `/mcp` 转发至该进程/容器，保留 Authorization 和 MCP 会话头，支持 Streamable HTTP，关闭流式响应缓冲。

Linux Node 运行时需支持 `--env-file`（至少 Node 20.6，实际安装与项目依赖兼容的受支持版本）。
进程管理配置见 `deploy/supabase-selfhost/systemd/crp-mcp.service`：它用 systemd 的
`EnvironmentFile` 读环境文件，因此**不依赖** Node 的 `--env-file`，`ExecStart` 也按服务器实际
`which node` 填写，不含本机的 `/opt/homebrew/bin/node`。

在 MCP 包目录的启动形式（两种都可以）：

```bash
npm run mcp:start:selfhost                       # = node --env-file=.env.selfhost.local src/index.mjs
node --env-file=.env.selfhost.local src/index.mjs
```

原来的 `npm run mcp:start` 不加载环境文件，现已另加 `mcp:start:selfhost` 入口。
使用专用 REVIEWER 账号，客户端只拿 MCP 地址和访问令牌。

提交状态不确定的补偿缺陷**已修复**：明确拒绝才回收空批次；结果不明时先向平台核对
`get_latest_linky_batch_import`，核对到已受理就按成功返回真实受理编号，核对不了就保留批次
并提示去平台确认。详见第 10.1 节，相关失败测试已覆盖。

### 7.4 Edge Functions

完整复制现有目录到 `/srv/crp/supabase/volumes/functions/`：

- `admin-model-config`：模型密钥配置必需。
- `skill-bundle-admin`：技能包上传/发布必需。
- `wechat-auth`：本版首轮不接公网微信登录；如果后续启用，需另行配置可访问的 OAuth 回调。

函数目录包含 `index.ts`、本地模块、`deno.json` 等依赖。当前代码通过 `esm.sh` 下载模块：部署服务器能访问时可预缓存；公司限制公网出站时需要在构建阶段打包/供应依赖，这属于少量部署适配。

配置运行时变量并明确注入 functions 容器，验证 legacy JWT/anon/service-role 兼容及函数内部管理员鉴权；不能通过关闭所有鉴权来处理不兼容。

Functions 内部连接可用 Docker 服务名，但文件签名链接必须使用公司浏览器可访问的 `https://supabase.corp.example`。现有签名 URL 如包含内部主机名，应调整为外部地址或相对路径，由前端拼接。

自部署 Functions 通过文件与环境变量部署。代码变更由 `apply-migrations.sh --apply` 同步
文件并重启 functions；环境变量变更仍需 recreate functions。不使用旧公网
`supabase functions deploy` 目标。

## 8. 安全、兼容、运行与回滚

- 新密码、JWT/Vault 密钥、API key、MCP 令牌独立生成；保留当前代码需要的 legacy key 兼容。切换新版 key 前须验证。
- 公司用户使用 HTTPS；数据库、管理接口限制管理员访问。浏览器只使用客户端 key。
- 配置 Auth 的 `SITE_URL`、允许回调和必要 SMTP/邮箱管理方式，避免跳回 localhost。首轮可由管理员预置账号。
- 配置 Docker Engine 开机启动，容器 `restart` 策略或 MCP systemd 自启动；用重启验收证明不依赖 Mac。
- 备份数据库、Storage 文件、配置及必要密钥、Worker 会话与相关卷，并存到另一位置；做恢复测试。
- 停止/更新 Worker 前检查在途任务；更新公司 Worker 采用确认目标后的排空流程。
- 回滚时停止新提交和新 Worker，保留公司环境数据，不自动启动原来的公网 Worker。
- 不删除原公网/本地开发数据；任何停止命令不得携带 `-v`。

## 9. 实施步骤与文件范围

### A. 公司服务器准备

由实施同事确认：服务器 IP、Linux 发行版、CPU 架构、资源、部署权限、Docker Engine/Compose、内网 DNS 与证书、Linky/GitLab/模型连通性，以及是否允许下载镜像和依赖。

Supabase 单独参考官方推荐 4 核、8 GB+ RAM、80 GB+ SSD；与 Worker 同机时额外评估内存、缓存磁盘和并发。上述推荐不代表已测量本平台全部服务的容量。

未验证公司服务器前，不把 Mac 的资源、端口或网络状态当成部署结论。

### B. 准备官方发行版

以下 `/srv/crp` 路径由公司部署人员先创建并授权；目录已存在时检查，不覆盖数据和密钥。

```bash
cd /srv/crp
git clone --depth 1 --filter=blob:none --sparse --branch self-hosted/v0.8.2 https://github.com/supabase/supabase.git supabase-source
git -C supabase-source sparse-checkout set docker
mkdir supabase
cp -R supabase-source/docker/. supabase/
cd supabase
cp .env.example .env
sh utils/generate-keys.sh
sh utils/add-new-auth-keys.sh
```

锁定官方版本与镜像，记录 `.supabase-version`，不要默认拉 `latest`。生成脚本可能输出秘密，不向聊天或提交日志转发。离线环境从公司仓库或离线包准备相应镜像/依赖。

### C. 配置 Supabase、Docker 网络与 HTTPS

新实例 `.env` 的非秘密配置（完整模板见
`deploy/supabase-selfhost/env/supabase.env.nonsecret.example`）：

```dotenv
COMPOSE_PROJECT_NAME=crp-selfhost
COMPOSE_FILE=docker-compose.yml:docker-compose.crp.yml
SUPABASE_PUBLIC_URL=https://supabase.corp.example
# 是基址，**不要**带 /auth/v1；官方 .env.example 的默认值就是 http://localhost:8000
API_EXTERNAL_URL=https://supabase.corp.example
SITE_URL=https://review.corp.example
ADDITIONAL_REDIRECT_URLS=
POOLER_TENANT_ID=crp-selfhost
POSTGRES_PORT=5432
POOLER_PROXY_PORT_TRANSACTION=6543
```

`docker-compose.crp.yml` 直接用 `deploy/supabase-selfhost/docker-compose.crp.yml`。
它在本机演练中核对过三件事：

- v0.8.2 里**只有 `api-gw` 与 `supavisor` 发布宿主机端口**。`POSTGRES_PORT`/
  `POOLER_PROXY_PORT_TRANSACTION` 是发布在 **supavisor** 上的（不是 db 服务），
  照官方默认会变成 `0.0.0.0:5432` —— 数据库入口直接暴露在公司网里。覆盖层把三个端口
  全收到 `127.0.0.1`（54341/54342/54343）。
- **`studio` 本来就不发布端口**，它走网关的 `/` 路由。早期草稿想给 studio 加
  `ports: !override` 限制访问，那是反效果：会**新增**一个暴露面。限制 Studio 的正确做法是
  反向代理只转发 API 前缀（见 `nginx/supabase.conf`），管理员走 SSH 隧道。
- 覆盖 `api-gw` 的 networks 时必须把官方的 `envoy` / `kong` 两个别名一并写回，
  否则 storage、studio 等容器解析不到网关。

`!override` 需要 Docker Compose 2.24.4+（`scripts/preflight.sh` 会检查）；版本不够时
ports 会**合并**而不是替换，端口照旧暴露，而部署看起来是成功的。

### 10.1 仓库侧已完成（2026-10-14，本机验证）

**一、修掉提交状态不确定的缺陷**（§3.3、§7.3 列为"提供给同事使用前必须修复"）。

原行为：`request_linky_batch_import_for_analysis` 一抛错就 `delete_review_batch`。问题在于
响应丢失（网关超时、连接被掐、502）可能发生在**事务已经提交之后** —— 那一刀删掉的是平台
已经受理的任务，回执还会说"平台上没有创建任何评审"，是假话。

改成三分支，判据是"服务端到底做了没有"而不是"有没有报错"：

| 情况 | 判据 | 行为 |
|---|---|---|
| 明确拒绝 | 4xx 且响应体是结构化 PostgREST 错误（事务已回滚） | 回收空批次，如实报失败 |
| 结果不明但核对到已受理 | 网络异常/5xx/408/429/非结构化响应 → 查 `get_latest_linky_batch_import` 查到导入单 | 按**成功**返回真实受理编号，并说明"核对过、没有重复提交" |
| 结果不明且核对不了 | 连核对请求也失败 | **批次原样保留**，回 `⚠️ 无法确认…请不要立即重复提交`，给出批次编号与平台链接和自查方法 |

配套改动：`PlatformError` 增加 `indeterminate` 标记（`isIndeterminateStatus()` 判 5xx/408/425/429
与非结构化响应）；新增 `SubmissionStateUnknownError` 与 `formatSubmissionUnknown()`；新增
请求超时 `CRP_PLATFORM_TIMEOUT_MS`（默认 30 秒，超时按"结果不明"处理，不再可能永久挂住）。

`npm run mcp:test` → **35 passed / 0 failed**（原 27 + 新增 8），新增用例覆盖：状态码分类、

明确业务拒绝→直接回收、200 无受理编号→先核对、不确定文本不含"已成功受理"也不含"没有创建"、

**据此修正的 7 处错误（原方案/模板写错，实测才发现）：**

1. `supabase db push --db-url` 的密码必须**百分号编码**，且必须显式 `sslmode=disable`，
   否则报 `tls error (The server does not support SSL connections)`。原命令会直接失败。
2. `API_EXTERNAL_URL` 是**基址**，原方案写成 `https://supabase.corp.example/auth/v1`。
3. 健康检查 `curl --fail .../auth/v1/health` **不带 apikey 返回 401**，看起来像部署失败。
4. 给 `studio` 加 `ports: !override` 是**反效果**（它本来不发布端口，加了等于新增暴露面）；
   限制 Studio 要靠反向代理只转发 API 前缀。同时发现覆盖 `api-gw` 的 networks 必须保留
   官方的 `envoy` / `kong` 别名。
5. `.env` 里**没有** `FILE_SIZE_LIMIT` 这个键（v0.8.2 写死在 compose 的 storage 服务里），
   往 `.env` 写是静默无效的。
6. **MCP 仍可能误删任务**（第一版修复不彻底）：客户端超时之后，服务端那笔事务可能**还在跑**，
   此刻"查不到导入单"并不证明没受理 —— 原逻辑据此删批次，删掉的正是一个稍后就会成立的任务，
   而且删除与提交交错还会留下指向已删批次的导入单。现在 `NOT_ACCEPTED` **只**来自服务端
   明确拒绝（4xx 业务错误＝事务已回滚）；结果不明时给在飞的事务留 3 次 ×2 秒的落地时间反复
   核对，查到按成功返回，始终查不到就报"结果不明"并**保留批次**。代价不对称：留一个看得见、
   可手工删的空批次，远好过删一个看不见、删不回的已受理任务。
7. **备份/恢复必须用 `supabase_admin`，不能用 `postgres`**。自部署里 `postgres`
   **不是 superuser**（`rolsuper=f`），用它恢复会在 `vault.secrets` 上报
   `permission denied for table secrets` —— 也就是**模型 API Key 恢复不出来**，
   而旧脚本用 `ON_ERROR_STOP=0` + `|| true` 把这条错误吞掉，于是一份丢了密钥的备份会被
   判定为"验证通过"。另外旧脚本把 `roles.sql` 灌进**活着的集群**，那是 `CREATE/ALTER ROLE`
   级别的语句，会改掉现有角色的口令与成员关系。现已改为：角色只**解析核对、绝不执行**；
   恢复用 `supabase_admin`；pg_restore 的错误全量打印并判定失败；核对项加上 `vault_secrets`。

### 10.5 未验证项

- **Edge Functions 的 `esm.sh` 依赖与 JWT 兼容**：必须在能访问外网（或已准备离线依赖）的
  目标机上实测，本机无法代替。
- **签名文件 URL 是否带内部主机名**：取决于自部署实例的 `SUPABASE_PUBLIC_URL` 实际配置，
  需在部署后用浏览器下载一个附件来确认。
- **Compose override 与官方 `self-hosted/v0.8.2` 的最终合并结果**：本机没有官方源文件，
  只验证了 Worker 那一份 override 的合并；Supabase 那份需在服务器上
  `docker compose config` 核对（输出含密钥，不要外传）。
- **恢复脚本已在演练实例的真实备份上跑过**（0 error，Vault 密钥恢复出来，集群角色未变），
  但未在公司服务器的正式备份上跑过，也未验证"全新空集群 + roles.sql"那条路径。
- 产品当前展示版本保持 **V1.47**：V1.48 的交付物是"公司内网能用的平台"，服务器侧未完成，
  不提前把展示版本推到 V1.48。
