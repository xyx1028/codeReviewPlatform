# 操作日志扩展为批次与模型配置审计

这组改动为批次创建/删除、模型创建、配置修改与启停补充审计，并通过对象快照和 `ON DELETE SET NULL` 保留删除后的历史。模型 RPC 保持 0010/0012 的签名和旧 Secret ID 返回协议，RLS 将模型事件限制给管理员，前端按批次/模型 action 分流。旧 `COMPLETE`、`REOPEN`、`MODEL_DISPLAY_NAME_UPDATED` 数据在加约束前得到快照回填。阻塞点是密钥约束并未实现声明的字段白名单，正常配置入口仍可把 URL 中的 token 写入日志。

Watch for: **高危、confirmed** — `old_values`/`new_values` 只拦截少量顶层键名，无法保证 API Key、Secret ID 或 token 值不落日志；**低危、confirmed** — 0015 的升级、RLS、触发器和密钥拒绝行为没有数据库回归测试。

**Verdict**: NEEDS_CHANGES

## High-level view

批次审计由创建触发器和删除 RPC 完成；日志保存名称与周标识，删除后外键将 `batch_id` 置空。已有批次事件先回填快照再收紧事件形状，兼容当前旧数据结构。

模型创建和更新继续走 service-role RPC，启停走带管理员校验的 authenticated RPC。参数、默认值和轮换时返回旧 Secret UUID 的协议未变化，前端可展示并发、超时、启停和 API Key 状态而不读取 Secret ID。

模型日志的 RLS 依赖 `public.is_admin()`，非管理员直接查表也只能看到批次事件。安全缺口位于日志 JSON 约束：它是少量键名黑名单，不是允许字段和值的白名单。

## 日志 JSON 仍可接收凭据值

**高危、confirmed。** `batch_operation_log_safe_values_check` 在 `supabase/migrations/0015_operation_log_audit.sql:109-121` 只用 JSONB `?|` 检查顶层键是否恰好等于 `api_key`、`api_key_secret_id`、`secret`、`secret_id`、`token`、`authorization` 或 `password`。`{"credentials":{"token":"..."}}`、`{"access_token":"..."}` 以及允许字段中的凭据值都能通过，与注释声明的“只允许显式白名单字段”不一致。

正常入口也可触发泄漏：模型创建在 `supabase/migrations/0015_operation_log_audit.sql:307-319`、更新在 `:391-437` 会原样记录 `base_url`，而 RPC 只校验非空并 trim。`https://host/v1?token=SECRET` 或含 userinfo 的 URL 会把凭据永久写入管理员可读的日志。应正向校验允许键和字段类型，并拒绝或清洗 URL 的 userinfo 与敏感查询参数；密钥轮换仍只记录 `api_key_changed`。

## 关键数据库行为没有迁移回归测试

**低危、confirmed。** `supabase/tests` 没有覆盖 0015 或 `batch_operation_log`。旧 `COMPLETE`/`REOPEN`/模型名称数据升级、创建触发器、删除后快照保留、非管理员 RLS、字段差异及密钥 JSON 拒绝都未被自动验证。

应增加迁移级 SQL 测试，以管理员、普通 authenticated 用户和 service role 执行关键路径，并包含嵌套/变体敏感键及 URL token 的负例。
