# 代码评审平台 V1.5：真实运行监控台实施方案

> 文档性质：可直接进入开发的实施基线，不是已完成能力说明。
> 本轮范围：仅设计与实施计划，不实施数据库、Worker 或前端代码。
> 适用基线：当前仓库迁移已编排至 `0031_freeze_manifest_and_canonical_policy_hash.sql`，执行引擎为 `deepseek-harness-acp`。
> 修订说明：本版补齐了 7 个阻塞级设计缺口（游标安全、全工具实时可见性、事件量控制、投影热行、权限边界、Job 层 fencing、遗漏的终态边界），并修正了与代码不符的事实描述。所有代码引用均已按当前仓库核对。

## 1. 目标与结论

V1.5 的监控系统有**两类消费者，需求不同且部分冲突**，设计必须同时满足：

| | 消费者 A：人（管理员 UI） | 消费者 B：AI（后续做问题分析、性能优化的 Agent） |
|---|---|---|
| 核心问题 | 现在卡在哪 | 时间花在哪、和上次比慢在哪、优化有没有生效 |
| 时间取向 | 当下，秒级新鲜度 | 历史，跨运行、跨版本可比 |
| 数据形态 | 增量游标 + 中文标签 | 一次性自包含快照 + 稳定机器码 |
| 数据量偏好 | 少而准，够渲染就行 | 完整可归因，宁多不缺 |
| 保留期 | 30 天足够 | 原始事件 30 天，**但聚合指标必须长期存活** |

两者冲突的地方有三处，必须显式解决，否则 AI 侧等于没有：

1. **游标增量接口不适合 AI。** `get_analysis_runtime_console` 为「每 2.5 秒补拉一点」设计，AI 需要的是「给我这次 attempt 的完整诊断包」。→ 单独提供诊断 RPC，见 §6.10。
2. **30 天保留期会删掉趋势基线。** 事件一清，「优化前 vs 优化后」就无从对比。→ 新增不随事件清理的每次运行汇总表，见 §6.9。
3. **只有事件流不足以回答「时间花在哪」。** 一堆带时间戳的点无法自动归因，且并发 Agent 的耗时会重叠。→ 定义显式的墙钟时间归因模型，含「无法解释的时间」桶，见 §6.9.2。

### 1.1 人视角：监控台要回答的问题

管理员可以从正在运行的批次逐层查看：

```text
批次 → Analysis Job → 需求任务 → Attempt/Run → Agent Tree → 当前真实活动
                                                       ├─ 模型请求
                                                       ├─ 工具调用
                                                       ├─ Workflow
                                                       └─ Harness Job
```

首版必须回答：

1. 哪些批次正在准备代码、分析需求或汇总结果。
2. 每个需求任务在等待、运行、成功还是失败，当前是第几次 Attempt。
3. 当前由 root Agent、研究 Agent、实现 Agent、批评 Agent 还是 workflow Agent 执行。
4. 每个并发 Agent 当前是在准备环境、请求模型、调用工具、执行 Workflow、等待子 Agent，还是正在收敛提交。
5. 当前活动从何时开始，最近一次事实事件何时到达，界面数据是否已陈旧。
6. 失败、取消、租约丢失和 Worker 关停分别发生在哪一层。

### 1.2 AI 视角：诊断与优化要回答的问题

这一节和 §2.1 的「UI 断言 → 真实边界」映射表同等地位：下面每个问题都必须有一条明确的查询路径能回答，没有路径的问题不允许留在这张表里假装能答。

| 分类 | 问题 | 回答依据 |
|---|---|---|
| 归因 | 这次 attempt 共 40 分钟，分别花在准备、模型、工具、收敛、无法解释各多少 | §6.9.2 时间归因模型 |
| 归因 | 哪个工具、哪个 Agent、哪次模型请求吃掉了最多墙钟时间 | §6.10 诊断 RPC 的 top-N |
| 归因 | 有多少时间是「Agent 已注册但没有任何未闭合请求」的空转 | `agent_idle_ms` |
| 并发 | 子 Agent 是真并行还是被串行化了 | `max_concurrent_agents` / `max_concurrent_tools` |
| 回归 | 同一模型、同一 policy 下，本周 attempt 比上周慢了多少 | §6.9 汇总表跨时间查询 |
| 回归 | 我上次的优化生效了吗（改动前后同类 attempt 对比） | 汇总表 + `profile_hash` / `policy_hash` / `harness_version` 分组 |
| 失败 | 这个 `error_code` 历史上出现过几次，都在哪个阶段 | 事件表 + 汇总表的 `terminal_error_code` |
| 失败 | 失败的 attempt 在失败前最后一个成功边界是什么 | 事件时间线倒查 |
| 浪费 | 有多少模型请求是 retry / compaction，即非有效推进 | `model_request_kind` 分桶 |
| 浪费 | 子 Agent 冲撞提交权、被角色策略拒绝了多少次 | `TOOL_CALL_DENIED` 计数 |
| 浪费 | 有没有 Agent 产出了 0 条证据却烧了大量预算 | 汇总表 per-agent 段 |
| 盲区 | 我们的插桩有没有漏（无法解释的时间占比多高） | `unattributed_ms / wall_ms` |
| 环境 | 慢是模型侧还是平台侧（模型等待 vs 工具执行 vs 数据库往返） | `model_ms_union` vs `tool_ms_union` vs `db_ms` |
| 可比性 | 两次 run 的差异只在哪个维度 | run 指纹：模型路由 + 四个 hash |

设计推论（这些直接约束了后面的 schema）：

- **必须有稳定机器码，不能有展示文案。** 数据库与 RPC 永不返回中文；中文只存在于 `src/lib/labels.ts`。这既是 UI 的 i18n 要求，也是 AI 可解析的前提。
- **必须有 run 指纹。** 每次运行要能标定「跑的是哪个模型、哪份 profile、哪份 policy、哪个 Harness 版本」，否则跨运行对比没有意义。这四个值现有表已有（`model_label`、`profile_config_hash`、`policy_hash`、`harness_version`），要一并进汇总表。
- **AI 通道只走数据库与日志，完全不经过前端界面。** 前端是给人看的，不承担 AI 取数职责。因此：
  - AI 侧数据的载体是「事件表 + 汇总表 + 结构化日志」三处，不需要任何 UI。
  - §6.10 的诊断 RPC 因此**不授予 `authenticated`**，只给 `service_role` 与 ADMIN，浏览器根本拿不到——比暴露给前端更安全，也少一层权限设计。
  - 取数通道是一个只读 CLI（§8.5），不是页面。
  - 汇总结果同时以单行结构化日志落一份（§13.1），作为数据库汇总失败时的独立备份通道。
- **必须承认盲区。** 归因模型里保留 `unattributed_ms`，这是发现「我们还没插桩到的地方」的唯一手段。宁可显示 30% 无法解释，也不要把它摊进其它桶假装归因完整。

### 1.3 核心结论

- **不能只靠现有状态表、日志或 `analysis_tool_audit` 做实时监控。** 必须新增 Worker 主动上报、数据库持久化的脱敏事实事件流，并保留可重建的当前活动投影。
- **必须插桩 Harness 进程内的工具与模型边界，否则第 4 条无法实现。** Broker 只有 13 条路由，对应 5 个平台快照工具；模型真正常用的 `bash / read / write / edit / grep / glob / web_search / web_fetch / workflow / job_* / subagent / todo_write` 全是 `origin: "harness"`，不经过 Broker。见 §7.4。
- **全部实时插桩通过扩展现有 Broker 路由的请求体实现，不新增路由。** 原因见 §7.2，这是避免部署排空窗口的硬约束。
- **游标必须带提交水位，否则断线补拉会永久丢事件。** 见 §6.1.3。

## 2. “真实”的定义

监控台中的每个运行节点和活动必须满足以下条件：

- 由实际执行边界产生，例如 Worker 成功领取任务、Agent 注册成功、工具进入 `tools/pre-execute`、模型请求预留通过、工具执行返回。
- 先有后端事实事件，再有前端展示；前端不得根据计数增长、工具名称或超时自行猜测阶段。
- 事件具有唯一幂等键、数据库递增游标、提交水位、发生时间和接收时间，可在断线后无缺口补拉。
- Agent 节点只有在 `register_analysis_agent_node` 成功后才算真实存在。
- 当前活动由事件更新投影；事件历史是事实源，投影只是快速查询结果。
- 多 Agent 并发时，按 Agent 节点分别展示当前活动；run 级活动是由 node 投影聚合出的“最近发生的活动”，不能冒充唯一活动。
- 未接入生命周期事件的 Workflow/Harness Job 必须显示“暂不可展开”或“未知”，不能伪造步骤树和完成百分比。

以下数据不是“真实运行事实”，不得用于声称正在执行某动作：

- Worker 普通结构化日志。
- Session JSONL 内容。
- `analysis_tool_audit` 中已完成且批量延迟落库的记录。
- `provider='workflow'` 本身推导出的 Workflow step。
- `job_list/job_output/job_kill` 工具名推导出的 Job 生命周期。
- Token 变化推导出的“模型正在思考”。
- `cost_micros`；见 §4.4。

## 3. 非目标

V1.5 不做以下事项：

- 不展示模型思维链、Prompt、源码正文、工具参数/响应、命令输出或 Session JSONL。
- 不把监控事件作为调度、租约续期、预算控制或提交校验的依赖。
- 不在首版直接依赖 Supabase Realtime；首版先使用带提交水位的游标轮询。
- 不读取 Worker 宿主机日志或 Session 卷作为浏览器数据源。
- 不修改现有 `analysis_agent_run` 作为 Attempt 的业务语义，也不新增重复的 Attempt 主表。
- **不新增 Broker 路由，不新增模型工具，不改动 `v4-capability-contract.json`**（首版）。原因见 §7.2。
- 不给 VIEWER 开放运行监控台；批次控制台采用 manage 语义，见 §6.7。
- 不在没有真实 Workflow/Harness Job 协议前展示虚构的步骤、PID、命令或进度。
- 不做全链路 metrics 出口；首版可观测性落在结构化日志字段与 SQL 聚合上，见 §13。
- **不把 AI 诊断数据搬进前端界面。** 归因、趋势、异常清单全部只存在于数据库与日志，通过 CLI 取用；前端只服务人的实时监控需求。UI 上的归因摘要是可选项，不是交付门槛。

## 4. 当前真实数据基线

### 4.1 已存在且可以复用的数据

| 数据源 | 当前真实含义 | 可用于监控 | 限制 |
|---|---|---|---|
| `analysis_job` | 批次分析 Job 及准备、处理、汇总终态 | Job 总状态、计数、错误、时间 | 没有细粒度运行事件 |
| `analysis_story_task` | 每个需求任务及当前 claim/Attempt | 任务状态、Worker、lease、attempt | 有三套状态列，见 §4.3；`agent_status` 只有四态 |
| `analysis_agent_run` | 一次真实 Attempt | Attempt 状态、累计 usage、取消/封存 | 没有 current activity；详情 RPC 只取最新 Attempt |
| `analysis_agent_node` | 已成功登记的 Agent Tree 节点 | Agent 角色、provider、父子关系、分 Agent usage、终态 | 没有每个 Agent 当前动作 |
| `analysis_tool_audit` | 工具完成后的安全审计 | 历史工具汇总、耗时、权限结果 | 每 32 条或 Broker close 才 flush，见 §4.5 |
| `analysis_permission_decision` | 策略层判定 | 后端审计 | 浏览器不可直接读（0027 已 `revoke all`） |
| `analysis_session_checkpoint` | Session locator/hash/checkpoint | 恢复诊断 | 含 locator，浏览器不可读；不是实时事件流 |
| `analysis_artifact` | Workspace 生成物元数据 | 产物摘要 | 不代表当前活动 |
| `analysis_agent_evidence` | 冻结 Commit 上的证据 | 结果追溯 | 不代表当前活动 |
| `analysis_worker_heartbeat` | Worker 可用性和槽位 | Worker 在线/繁忙状态 | 5 秒间隔，不能承载高频 UI 活动 |
| `admin_list_analysis_workers()` | 在线 Worker 与其正在处理的批次 | 顶部 KPI 直接复用 | 内部已有 `ensure_admin()`；见 §6.6 |

`list_active_analysis_workers()` 已在 `0019` 被 `drop`，不要引用。

### 4.2 当前状态值必须原样遵循

- `analysis_job.status`：`QUEUED | PREPARING_CODE | PROCESSING | FINALIZING | SUCCEEDED | FAILED`
- `analysis_story_task.agent_status`：`PENDING | RUNNING | SUCCEEDED | FAILED`（**没有 CANCELLED**）
- `analysis_agent_run.status`：`RUNNING | COMMITTED | FAILED`（**没有 CANCELLED**；取消落成 `FAILED` + `error_code='AGENT_TREE_CANCELLED'`）
- `analysis_agent_node.status`：`RUNNING | FINISHED | FAILED | CANCELLED`
- Agent role：`root-reviewer | research-child | implementation-child | critic-child | workflow-child`
- Agent provider：`root | spawn | fork | workflow | ralph`
- 工具判定：`ALLOW | DENY | CANCELLED`

事件类型有自己的词表（例如 `ATTEMPT_CANCELLED`），它**不是** run 状态，实现时不要试图把它写进 `analysis_agent_run.status`。

前端当前 `src/types.ts:409` 把 run 状态误写成 `'RUNNING' | 'FINISHED' | 'FAILED' | 'CANCELLED'`；`src/types.ts:450` 的 `input_tokens: number` 不是 nullable。Phase 0 必须先改成数据库真实值，并将 Token 类型改为 nullable；数据库没有上报 Token 时界面显示“未上报”，不能显示 `0`。

### 4.3 `analysis_story_task` 有三套状态列

`retrieval_status`、`analysis_status`（均来自 `0010`）与 `agent_status`（`0017` 新增）并存。现有 `listAnalysisStoryTasks`（`src/lib/api.ts:659`）用 `select('*')` 会一次拿到三套。

监控台**只认 `agent_status`**。DTO 里不返回另两个字段，避免再次出现“界面显示 PENDING 其实在跑”。

### 4.4 `cost_micros` 的处置

全仓检索确认：`cost_micros` 只在 `0027` 有建列（`0027:267`）和非负 CHECK（`0027:292`），**没有任何写入源**，`save_agent_review_result` 的 `p_usage` 解析也不含该键。

V1.5 决策：**不接入计费**。DTO 不返回该字段，UI 不出现成本相关文案。若后续要接，单独立项（需要模型单价表 + token → 成本换算 + 汇率/版本管理），不要在监控台里留一个永远为 null 的“成本”让人当 bug 查。

### 4.5 已确认的实时性缺口

1. 没有 append-only、浏览器可消费、可按游标补拉的事件表。
2. 没有 `current_activity` 投影。
3. `get_analysis_agent_run_detail`（`0027:2259`）只返回 `agent_attempt desc limit 1` 的最新 Attempt，不支持历史 Attempt timeline。
4. 工具审计在工具完成后生成，且只有 `auditEntries.length >= 32`（`attempt-control-broker.ts:245/327`）或 `close()`（`:938`）才 flush；`recordDecision`（`:334`）**从不触发 flush**，permission decision 只能搭下一次 entry 的 flush 或 close 那一次。因此 audit 无法表示“正在调用”。
5. 没有 Workflow instance/step 的持久生命周期。
6. `AttemptTreeController.jobs` 明确传入 `null`（`deepseek-harness-acp-engine.ts:495-497`），平台没有 Harness Job 清单。
7. 没有 Supabase Realtime publication、`postgres_changes` 订阅、SSE 或 WebSocket；没有 pg_cron 或任何定时清理函数。
8. 当前页面使用固定间隔快照轮询，没有断线游标补偿：`src/App.tsx:1210/1219/1225` 为 4 秒，`src/pages/AgentRunDetailPage.tsx:54` 为 4 秒，`src/pages/WorkerManagementPage.tsx:90/98` 为 5 秒。

设计原则：

- 事件表不参与 lease heartbeat，避免监控故障影响调度安全。
- 安全/身份/提交类操作仍由现有治理 RPC 决定，监控事件不可改变业务结果。
- 运行中事件写失败可短暂缓冲重试；终态事件在现有数据库终态 RPC 内原子写入。
- 不发送模型流式 Token chunk、heartbeat 成功事件或逐行命令输出，避免无界事件量。
- 快照可从业务表和投影重建；游标事件用于低延迟更新和时间线。
- 高频投影只写 `analysis_agent_node`（每个 Agent 一行，天然分片），不写 `analysis_agent_run` 热行。

### 6.1 `analysis_runtime_event` 事实表

以下 DDL 是实施时的基线形状；开发时可调整约束写法，但不得改变安全边界和游标语义。

```sql
create table public.analysis_runtime_event (
  id bigint generated always as identity primary key,
  -- 提交水位。id 在 INSERT 时取号，可见性按提交顺序，两者不一致；查询侧必须用
  -- xact_id 与 pg_snapshot_xmin 裁剪，否则并发写入会让游标永久跳过事件。见 6.1.3。
  xact_id bigint not null default pg_current_xact_id()::text::bigint,
  event_uuid uuid not null unique,
  schema_version smallint not null default 1 check (schema_version = 1),

  batch_id uuid not null references public.review_batch(id) on delete cascade,
  job_id uuid not null references public.analysis_job(id) on delete cascade,
  task_id uuid references public.analysis_story_task(id) on delete cascade,
  agent_run_id uuid references public.analysis_agent_run(id) on delete cascade,
  agent_node_id uuid references public.analysis_agent_node(id) on delete set null,

  worker_id text,
  scope text not null check (scope in (
    'JOB', 'TASK', 'ATTEMPT', 'AGENT', 'MODEL', 'TOOL', 'WORKFLOW', 'HARNESS_JOB'
  )),
  event_type text not null,
  activity_code text,
  phase text check (phase is null or phase in ('STARTED', 'TERMINAL')),
  status text,
  correlation_id text,
  parent_correlation_id text,
  error_code text,
  duration_ms integer check (duration_ms is null or duration_ms >= 0),
  payload jsonb not null default '{}'::jsonb,

  occurred_at timestamptz not null,
  received_at timestamptz not null default now(),
  -- 预留的分区键。由 RPC 从钳制后的 occurred_at 确定性推导，重试时值不变。
  -- 现在不用于分区，但将来切分区时约束可换成 unique (event_uuid, event_day)
  -- 而不破坏幂等。见 6.1.1。
  event_day date not null,
  clock_skewed boolean not null default false,
  retention_until timestamptz not null default (now() + interval '30 days'),

  check (octet_length(payload::text) <= 2048),
  check (scope in ('JOB') or task_id is not null),
  check (scope not in ('ATTEMPT', 'AGENT', 'MODEL', 'TOOL', 'WORKFLOW', 'HARNESS_JOB')
         or agent_run_id is not null),
  check (scope not in ('MODEL', 'TOOL', 'WORKFLOW', 'HARNESS_JOB')
         or correlation_id is not null)
);

-- 主查询路径：按批次 + 游标，且要能按 xact_id 裁剪水位。
create index idx_analysis_runtime_event_batch_cursor
  on public.analysis_runtime_event(batch_id, id) include (xact_id);
create index idx_analysis_runtime_event_task_cursor
  on public.analysis_runtime_event(task_id, id) where task_id is not null;
create index idx_analysis_runtime_event_run_cursor
  on public.analysis_runtime_event(agent_run_id, id) where agent_run_id is not null;
-- 未闭合 correlation 查询：“现在还有哪些工具/模型请求在跑”。
create index idx_analysis_runtime_event_open_correlation
  on public.analysis_runtime_event(agent_run_id, correlation_id)
  where phase = 'STARTED';
create index idx_analysis_runtime_event_retention
  on public.analysis_runtime_event(retention_until);
```

字段语义：

- `id`：数据库单调取号，用于排序与分页，不作为业务身份，**单独使用不安全**。
- `xact_id`：写入事务号。查询侧据此计算安全水位。
- `event_uuid`：Worker 在首次上报前生成，重试复用，数据库 `on conflict` 幂等；也是前端去重键。
- `occurred_at`：执行边界实际发生时间。
- `received_at`：数据库接收时间，用于计算链路延迟。
- `event_day`：预留分区键，由钳制后的 `occurred_at` 取 `::date`。见 §6.1.1。
- `clock_skewed`：`occurred_at` 超出容许偏差时置真，UI 据此提示，而不是丢弃事件。
- `correlation_id`：一次工具、模型、Workflow 或 Harness Job 生命周期的稳定随机 ID，由产生方生成，不得使用命令、URL 或路径。
- `phase`：`STARTED` 表示该 correlation 尚未闭合；`TERMINAL` 表示闭合。`null` 用于无生命周期的点事件（如 `PINS_VERIFIED`）。这是“正在调用”的唯一判据。
- `activity_code`：稳定机器码；中文名称由前端映射，Worker 不上传任意展示文案。
- `payload`：仅允许事件契约定义的安全标量字段，见 §6.5。
- `retention_until`：默认保留 30 天；终态业务表和聚合 usage 不随事件清理。

#### 6.1.1 分区决策：不分区，但预留分区键

**结论：`0032` 不建分区，同时加入 `event_day` 列为将来切分区预留。**

原因是分区在 PostgreSQL 上和本方案的幂等机制直接冲突，已实测确认：

```
create table probe (
  id bigint generated always as identity primary key,
  event_uuid uuid not null unique,
  received_at timestamptz not null default now()
) partition by range (received_at);

ERROR:  unique constraint on partitioned table must include all partitioning columns
DETAIL:  PRIMARY KEY constraint on table "probe" lacks column "received_at"
         which is part of the partition key.
```

分区表的唯一约束**必须包含分区键**，所以 `unique (event_uuid)` 建不出来。退成 `unique (event_uuid, received_at)` 更糟：`received_at` 默认是 `now()`，每次重试都是新值，约束永远不触发，§6.6 的「同一 `event_uuid` 重试 10 次只产生一行」会彻底失效，Worker 重试将写出重复事件。

因此：

| | 不分区（采用） | 分区 |
|---|---|---|
| 幂等 | `unique (event_uuid)`，一条约束搞定 | 必须重新设计，不能用 `ON CONFLICT` |
| 清理 30 天前数据 | `purge_analysis_runtime_events(p_limit)` 分批 DELETE + `retention_until` 索引 | `DROP TABLE` 分区，瞬间完成 |
| 表膨胀 | 依赖 autovacuum 回收死行 | 无死行 |
| 迁移复杂度 | 低 | 高 |

`event_day` 的作用是让将来的切换成为机械操作而不是重新设计：它由**钳制后的 `occurred_at`** 推导（而不是 `received_at`），而 `occurred_at` 是执行边界时间，Worker 重试时复用同一个值 → `event_day` 对重试稳定 → 将来按它分区并把约束换成 `unique (event_uuid, event_day)` 时，幂等仍然成立。

切换时机：当 §10.6 的实测量显示单日事件超过 100 万，或表行数接近 5000 万时，另开一个 contract migration 做「建分区表 → 搬数据 → 改名切换」，需要停机窗口。有了 `event_day`，那次迁移不需要改任何 Worker 或前端代码。

注意：`occurred_at` 被钳制（`clock_skewed = true`）时，钳制目标必须是**确定性的**，否则重试会落到不同的 `event_day`。规则是钳到 `date_trunc('second', received_at)` 之后**由 RPC 返回实际写入值**，Worker 重试时携带首次返回的 `occurred_at` 而不是重新取本地时钟。这条在 §6.6 实现要求里再强调一次。

#### 6.1.2 为什么不复用 `analysis_tool_audit`

两者职责不同，必须并存：

| | `analysis_tool_audit` | `analysis_runtime_event` |
|---|---|---|
| 目的 | 完成后的安全审计 | 运行中的生命周期可见性 |
| 时机 | 工具结束后，批量 flush（32 条 / close） | 边界发生即入队，≤1s flush |
| 语义 | 一条记录 = 一次完成的调用 | 两条记录 = start + terminal（可折叠成一条） |
| 覆盖 | Broker 路由 + 插件上报的拒绝 | 全部 30 个模型工具 |
| 保留 | 长期 | 30 天 |

不删除、不改动 audit 的现有 flush 逻辑。前端“正在调用”只认未闭合的 `phase='STARTED'` 事件与 node 投影，不认 audit。

#### 6.1.3 游标安全：提交水位裁剪（阻塞级修正）

`bigint generated always as identity` 在 INSERT 时取号，但行的可见性按**提交顺序**。4 个 Worker × 多 attempt 并发写同一张表时，`id=100` 的事务完全可能比 `id=105` 的事务晚提交。轮询把游标推到 `max(id)` 之后，那条 id 更小、提交更晚的事件将**永久不可见**。

这会直接推翻 §15 的上线门槛「断线可通过 cursor 完整补拉」。必须在 Phase 0 定案。

**已在本地 Supabase（PostgreSQL 17.6）实证复现**，过程如下：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 事务 A 先取号（`id=1`, `xact_id=44809`），保持未提交 | — |
| 2 | 事务 B 后取号（`id=2`, `xact_id=44812`），立即提交 | — |
| 3 | 读者查询（A 仍未提交） | 只看到 `id=2` |
| 4 | 朴素游标推进到 `max(id)` | 推进到 **2** |
| 5 | 水位游标推进 | 停在 **0**（正确拒绝越过未提交的 A） |
| 6 | A 提交后，朴素游标查 `id > 2` | 返回 **0 行**，`id=1` 永久丢失 |

同时验证了本节 SQL 写法在 PostgreSQL 17.6 上均可执行：`pg_current_xact_id()::text::bigint`（`xid8` 无法直接转 `bigint`，必须经 `text`）、在列 `DEFAULT` 中调用它、以及 `octet_length(payload::text) <= 2048` 作为 CHECK 约束（`jsonb_out` 是 immutable，约束被接受）。

**采用方案：事务号水位。**

```sql
-- 查询 RPC 内计算，只服务已经全局稳定的事件
v_watermark := pg_snapshot_xmin(pg_current_snapshot())::text::bigint;

select ... from public.analysis_runtime_event
where batch_id = p_batch_id
  and id > coalesce(p_since_event_id, 0)
  and (
    xact_id < v_watermark
    -- 逃生阀：一个长事务（迁移、advisory lock）不能把整条监控链路卡住。
    -- Reporter 的单次 flush 有 10 秒硬超时，所以超过 30 秒的事件不可能还在未提交事务里。
    or received_at < now() - interval '30 seconds'
  )
order by id
limit 500;
```

`xact_id < xmin` 的行，其写入事务必然已经结束（提交或回滚），因此 `id` 顺序等于可见顺序，`id > cursor` 不会跳号。

配套要求：

- `next_event_id` 只能推进到本次返回结果中满足水位条件的最大 `id`，不能取表内 `max(id)`。
- 返回 `watermark_lag_ms`（`now() - 最老未过水位事件的 received_at`），UI 在超过 3 秒时提示“事件确认延迟”。
- 前端仍按 `event_uuid` 去重，作为第二道保险。
- `pg_current_xact_id()` 需要 PostgreSQL 13+；本地 Supabase 实测为 17.6，满足。旧名 `txid_current()` / `txid_snapshot_xmin(txid_current_snapshot())` 不要混用。部署前用 `select version()` 确认生产实例版本。
- `pg_current_xact_id()` 会分配真实 xid。事件写入本来就是 INSERT，不引入额外开销，但**不要**在只读路径调用它。

### 6.2 当前活动投影（分层，避免热行）

高频活动只写 `analysis_agent_node`。这张表每个 Agent 一行，是天然的分片键，且**没有 `touch_updated_at` 触发器**（`0027:311` 的 DDL 只有 `created_at`），不会因每次事件触发额外写。

```sql
alter table public.analysis_agent_node
  add column if not exists current_activity_scope text,
  add column if not exists current_activity_code text,
  add column if not exists current_activity_status text,
  add column if not exists current_correlation_id text,
  add column if not exists current_tool_name text,
  add column if not exists current_activity_started_at timestamptz,
  add column if not exists current_activity_updated_at timestamptz,
  -- 裸 bigint，不加外键：它是游标语义不是关系语义。加外键会让每次 retention 删除
  -- 都回写业务表，并与 analysis_runtime_event.agent_node_id 形成互相引用。
  add column if not exists current_activity_event_id bigint;
```

`analysis_agent_run` 只保存 **ATTEMPT scope 的阶段**（一次 attempt 约 10~15 条，低频，不构成热行）：

```sql
alter table public.analysis_agent_run
  add column if not exists attempt_phase_code text,
  add column if not exists attempt_phase_started_at timestamptz,
  add column if not exists attempt_phase_event_id bigint;
```

**run 级“当前在做什么”不落列**，由 `get_analysis_runtime_console` 在查询时聚合：

```text
run 当前活动 = attempt_phase_code
             + (select ... from analysis_agent_node
                where agent_run_id = run.id and current_activity_status = 'RUNNING'
                order by current_activity_updated_at desc limit 1)
```

投影规则：

1. 同一 node 仅接受 `event.id > coalesce(current_activity_event_id, 0)` 的更新，防止重试乱序回退。
2. `phase='STARTED'` 写入 scope/code/tool_name/correlation、`status='RUNNING'` 与 started time。
3. `phase='TERMINAL'` 且 `correlation_id` 与 `current_correlation_id` 相同时，把 status 置为终态；若 correlation 不同，说明已有更新的活动，**不覆盖**。
4. `analysis_agent_node` 终态（`mark_analysis_agent_node_terminal`）时清空 `current_activity_*` 运行态，保留最后 event id 与更新时间。
5. Attempt 终态（`save_agent_review_result` / `fail_agent_review`）与租约回收（`reclaim_stale_story_task_leases`）必须在同一事务里**批量清空该 run 下所有 node 的 `current_activity_*`**。漏掉这条会让监控台永久显示一个已死 Worker 的“正在调用工具”。
6. 投影更新与事件 insert 在同一数据库函数事务内完成。
7. 并发真相以 node 投影数组为准；run 级聚合只是摘要。

| `MODEL_REQUEST_DENIED` | TERMINAL | agent、correlation、`model_request_kind`、error_code | 预算/身份拒绝，provider 未被联系 |
| `MODEL_REQUEST_STARTED` | STARTED | agent、correlation、`model_request_kind` | reserve 通过、`next()` 调用前 |
| `MODEL_REQUEST_COMPLETED` | TERMINAL | correlation、duration、可空 token | token 未上报时保持 null |
| `MODEL_REQUEST_FAILED` | TERMINAL | correlation、duration、error_code | 不存 provider 原文错误 |

#### 工具（scope = TOOL）

| event_type | phase | 必需字段 | 备注 |
|---|---|---|---|
| `TOOL_CALL_STARTED` | STARTED | agent、correlation、`tool_name` | `tools/pre-execute` 放行后、`next()` 前 |
| `TOOL_CALL_COMPLETED` | TERMINAL | correlation、duration | 不存参数和返回内容 |
| `TOOL_CALL_FAILED` | TERMINAL | correlation、duration、error_code | `next()` 抛出 |
| `TOOL_CALL_DENIED` | TERMINAL | correlation、tool、`reason_code` | 角色策略拒绝，未进入 execute |
| `TOOL_CALL_CANCELLED` | TERMINAL | correlation、duration | attempt 收敛时对未闭合 correlation 补写 |

`TOOL_CALL_CANCELLED` 的补写责任在数据库侧：Attempt 终态 RPC 与 `reclaim_stale_story_task_leases` 必须把该 run 下所有 `phase='STARTED'` 且无对应 TERMINAL 的 correlation 补一条 CANCELLED。否则 Harness 进程被 SIGKILL 时会留下永远“正在调用”的孤儿。

#### Workflow / Harness Job（Phase 3）

Phase 3 新增真实 Broker 协议后才允许产生：`WORKFLOW_STARTED`、`WORKFLOW_STEP_STARTED`、`WORKFLOW_STEP_COMPLETED/FAILED/CANCELLED`、`WORKFLOW_COMPLETED/FAILED/CANCELLED`、`HARNESS_JOB_STARTED`、`HARNESS_JOB_RUNNING`、`HARNESS_JOB_COMPLETED/FAILED/KILLED`。

在 Phase 3 前，`provider='workflow'` 只能显示“Workflow 子 Agent 已注册”，并且它调用 `workflow` 工具时会正常产生 `TOOL_CALL_STARTED/COMPLETED`（因为它经过 `tools/pre-execute`）；`job_*` 工具同理只显示工具调用，不显示 Job 实例树。

### 6.4 Job 层 fencing 规范（阻塞级补充）

`JOB_*` 与 `REPOSITORY_*` 事件发生在**没有 task claim** 的阶段，不能套用 task 的四要素校验。真实的 fencing 令牌是：

| 阶段 | 校验对象 | 判据 |
|---|---|---|
| 准备代码 | `analysis_job.worker_id` | `= p_worker_id` 且 `status = 'PREPARING_CODE'` |
| 汇总 | `analysis_job.finalizer_worker_id` + `finalize_lease_expires_at` | `= p_worker_id` 且 lease 未过期 且 `status = 'FINALIZING'` |
| 任务级及以下 | `analysis_story_task` 四要素 | `worker_id` + `lease_expires_at >= now()` + `claim_token_digest = agent_claim_token_digest(p_claim_token)` + `agent_attempt` |
| 收敛路径（提交后） | `analysis_agent_run.session_revision` | claim 已被清空，只能用 revision，见 §6.4.1 |

不符合的事件一律拒绝并返回稳定错误码，不允许“校验不了就放行”。

#### 6.4.1 提交后 claim 被清空的连带后果

`save_agent_review_result`（`0027:2010`）与 `fail_agent_review` 在成功时会把 `claim_token_digest`、`worker_id`、`lease_expires_at` 全部置 null。

后果比表面更广：引擎 `finally`（`engine:790`）里的 `commitUsage`、`saveArtifact`、`saveSessionCheckpoint`、`markAgentTerminal`，以及 `controller.drain` 的 `fence`，在提交成功后**全部**会因 claim 失效而失败（当前靠 `.catch()` 吞掉）。

因此规则是：

- 收敛路径上的监控事件**不得依赖 claim token 校验**。
- Attempt 终态、Agent 终态、未闭合 correlation 的 CANCELLED 补写，全部在终态 SQL RPC 内完成，不由 Worker 事后补写。
- Worker 侧如果确实需要在收敛后上报（例如 `PROCESS_TREE_CLEANUP_FAILED`），用 `agent_run_id + session_revision` 做 fencing，并接受“已封存的 run 拒绝写入”这一结果。

### 6.5 Payload 安全白名单

允许按事件类型使用的字段：

- `agent_role`、`provider`、`delegation_depth`
- `tool_name`（必须命中 `v4-capability-contract.json` 的 `modelTools` 键或 Broker 路由桶名）、`permission_verdict`、`reason_code`
- `model_request_kind`（`loop | retry | compaction | session-title | ralph | other`）
- `repository_name`（必须来自 `analysis_repository_snapshot` 的仓库枚举）
- `attempt_number`、`session_revision`
- `request_bytes`、`response_bytes`、`input_tokens`、`output_tokens`
- `agent_count`、`active_children`、`duration_ms`
- `collapsed`（布尔，表示这条 TERMINAL 由 §7.3 折叠产生，没有独立的 STARTED 行）

**诊断扩展字段**（为 §1.2 的 AI 归因需求新增，逐项枚举，仍不含任何内容正文）：

| 字段 | 适用工具 | 为什么安全 | 为什么有用 |
|---|---|---|---|
| `exit_code` | `bash` | 整数，不含命令与输出 | 区分「工具慢」与「工具一直失败重试」 |
| `output_bytes` | `bash`、`read`、`grep`、`glob` | 只是字节数 | 定位「读了个巨大文件」这类浪费 |
| `truncated` | 快照读、`grep`、`glob`、`read` | 布尔 | 截断意味着 Agent 拿到的是残缺上下文，常是返工根因 |
| `hit_count` | `search_snapshot_code`、`grep`、`glob` | 整数 | 0 命中的检索是纯浪费；命中过多说明查询太宽 |
| `line_span` | `read_snapshot_code`、`read` | 整数行数，不含路径与内容 | 与 `output_bytes` 一起判断上下文膨胀 |
| `retry_index` | 模型请求 | 整数 | 直接看出重试深度 |

明确仍然禁止：命令文本、stdout/stderr 正文、文件路径（`repository_name` 除外，它是枚举）、查询串本身。判断标准是「这个字段能不能反推出源码或凭据」——上表六项都不能。
- 随机生成的 `workflow_id`、`workflow_step_id`、`harness_job_id`（Phase 3）

严禁保存：

- Prompt、模型输入输出、思维链、需求正文、源码。
- 工具参数、工具返回、命令、stdout/stderr、构建日志正文。
- 完整 URL、URL query、Authorization header、Cookie。
- API Key、token、claim token、Broker token、Agent capability token。
- 绝对路径、Session `storage_locator`、宿主机目录、Workspace locator。
- 浏览器 locator、选择器、未经枚举的文件路径。
- 任意 Worker/插件自报的中文描述或原始异常 message。

数据库函数必须按 `event_type` **重建**允许 payload，不能把上报的 JSON 原样写入。未知字段丢弃；未知 `event_type` 拒绝。

实现要求：

1. 仅 `service_role` 可执行 `report_analysis_runtime_event_batch`；`insert_analysis_runtime_event` 对所有角色 `revoke execute`。
2. 按 §6.4 的表校验 fencing。一批事件共享同一组 claim 凭据，校验一次。
3. `p_events` 里每条的 `agent_id` 非空时必须解析到同一 run 的 `analysis_agent_node`；解析不到则**丢弃该条并计数**，不整批失败（子 Agent 注册与首次工具调用之间存在窗口）。
4. 通过 `job_id` 反查并固化 `batch_id`，不接受上报的 batch。
5. `event_uuid` 冲突时返回原 `id`，**不重复更新投影**。
6. `occurred_at` 与数据库时间偏差超限（未来 > 60 秒、过去 > 24 小时）时，保留事件、置 `clock_skewed = true`、`occurred_at` 钳到 `received_at`，不破坏游标排序。
7. 写事件与更新投影在同一事务内。
8. 纯观测事件失败不回滚业务操作，但 Worker 要进入有界重试队列并上报丢弃计数。
9. 返回体包含 `accepted`、`duplicated`、`dropped_unresolved_agent`、`max_event_id`，供 Worker 记日志与自检。
10. 按仓库惯例：`security definer` + `set search_path = public`，先 `revoke execute from public, anon` 再按需 `grant`。

### 6.8 RLS、授权与保留期

- `analysis_runtime_event` 启用 RLS。
- 禁止 `anon` 所有权限；`revoke all ... from anon, authenticated`。
- insert/update/delete 不授予 `authenticated`，写入只走 service-role RPC。
- 首版浏览器不直接 SELECT 事件表，全部走 security definer 查询 RPC。
- Phase 5 如用 `postgres_changes`，再增加只允许 `can_manage_review_batch(batch_id)` 的 SELECT policy，并逐环境验证 Realtime 是否执行 RLS。
- 保留期清理：新增 `purge_analysis_runtime_events(p_limit integer default 50000) returns integer`，删除 `retention_until < now()` 且所属 Job 已终态的事件，**按批限量**，避免一次删除持有长事务把 §6.1.3 的水位卡住。
- 活动 Job 的事件即使 `clock_skewed` 也不得清理。
- 仓库没有 pg_cron。调度方式：由 Worker 的 `runPeriodicCleanup()`（`worker/src/index.ts:429`，已有 10 分钟节流）附带调用一次，或由运维侧定时任务调用。两者选一并写进部署文档，不要假设存在自动调度。
- 清理失败不得影响分析任务，需有删除行数与失败日志。
- **`analysis_agent_run_rollup`（§6.9）不参与上述清理，长期保留。** 事件是可丢的细节，汇总是不可丢的基线。

#### 6.9.2 墙钟时间归因模型

没有明确定义的归因模型，任何后续性能分析都是猜。定义如下，全部可由事件流计算：

```text
wall_ms          = ATTEMPT 终态事件 − ATTEMPT_STARTED
setup_ms         = HARNESS_PROCESS_STARTED − ATTEMPT_STARTED
                   （含 verifyPins / workspace / broker / profile / root 注册）
model_ms_union   = 所有 MODEL correlation [start, end] 区间的并集长度
tool_ms_union    = 所有 TOOL  correlation [start, end] 区间的并集长度
busy_ms_union    = (MODEL ∪ TOOL) 区间的并集长度
teardown_ms      = ATTEMPT 终态 − 最后一个 TERMINAL 事件
                   （artifact 登记 / checkpoint / 提交 / drain）
agent_idle_ms    = Σ 每个 Agent「已注册未终态但无未闭合 correlation」的时长
unattributed_ms  = wall_ms − setup_ms − busy_ms_union − teardown_ms
```

三条硬规则：

1. **union 与 sum 都要存。** `sum` 是总消耗（并发下会超过 `wall_ms`），`union` 是真实占用的墙钟。只存 sum 会得出「模型花了 80 分钟但 attempt 只跑了 40 分钟」这种无法解释的结果；只存 union 会看不出并行度。`model_ms_sum / model_ms_union` 就是有效并行倍数。
2. **`unattributed_ms` 允许为大值，不许被摊平。** 它是插桩盲区的度量。首版预期偏高（Harness 内部的编排、上下文组装、ACP 往返都还没插桩），这正是它的价值——它会告诉我们下一步该插哪里。若它 `/ wall_ms > 40%`，§13 应该告警。
3. **区间并集必须在 SQL 里算。** 标准做法是按 `occurred_at` 排序后用窗口函数做区间合并（`max(end) over (order by start rows between unbounded preceding and 1 preceding)` 判断是否与前序重叠，累计分组后取每组 `min(start)`、`max(end)`）。不要在应用层算——事件量大且 AI 可能直接查 SQL。

#### 6.9.3 写入时机与容错

- 由 `save_agent_review_result` / `fail_agent_review` / `reclaim_stale_story_task_leases` 在**同一事务**内调用 `compute_analysis_run_rollup(p_agent_run_id)`。
- 汇总计算失败**不得**回滚业务终态。实现方式：终态 RPC 里只写一条待办标记（`rollup_version = 0`），由 Worker 的周期任务或补偿 RPC `backfill_analysis_run_rollups(p_limit)` 异步补算。这样既保证不丢，也保证不拖累提交路径。
- 汇总幂等：主键是 `agent_run_id`，重复计算走 `on conflict do update`。
- 事件已被清理的老 run 无法重算——所以汇总必须在事件还在的时候算出来，这也是它 30 天内必须完成的原因。

### 6.10 AI 诊断查询 RPC

游标接口不适合 AI，需要单独入口。三个，全部只读。

**授权：只 `grant execute` 给 `service_role`，另加 `ensure_admin()` 允许 ADMIN 经 CLI 调用；不授予 `authenticated`。** 理由是这些 RPC 服务的是 AI 与运维，不服务浏览器（§1.2），所以从一开始就不进入前端的攻击面。它们返回的数据量也远超页面所需，暴露给浏览器只有坏处。

```sql
revoke execute on function public.get_analysis_attempt_diagnostics(uuid, integer)
  from public, anon, authenticated;
grant execute on function public.get_analysis_attempt_diagnostics(uuid, integer)
  to service_role;
-- 另两个同理
```

```sql
-- 1) 单次 attempt 的完整自包含诊断包。AI 排查「这次为什么慢/为什么失败」的主入口。
get_analysis_attempt_diagnostics(
  p_task_id uuid,
  p_agent_attempt integer default null   -- null = 最新
) returns jsonb
```

返回内容（一次取全，不分页）：

- `fingerprint`：模型路由 + 四个 hash + policy_version + prompt_version。
- `attribution`：§6.9.2 全部字段，含 `unattributed_ms` 与占比。
- `phases`：ATTEMPT scope 事件序列及各阶段耗时。
- `agents`：Agent Tree + per-agent 归因 + `idle_ms`。
- `slowest_tools` / `slowest_model_requests`：各 top 20，含 `tool_name`、`agent_role`、`duration_ms`、`error_code`。
- `failures`：全部 `*_FAILED` / `*_DENIED` 事件，按 `error_code` 聚合 + 首次出现时间。
- `open_at_end`：终态时仍未闭合的 correlation（插桩漏洞或进程被杀的证据）。
- `timeline`：完整事件序列（若超过 5000 条则按 scope 降采样，并显式返回 `timeline_truncated` 与 `timeline_sampled_scopes`，**不静默截断**）。
- `instrumentation_health`：`events_reported` / `events_dropped` / `unattributed_pct`，告诉 AI 这份数据本身可信度多少。

```sql
-- 2) 跨运行趋势与回归对比。AI 回答「优化生效了吗」「什么时候开始变慢的」。
get_analysis_run_trend(
  p_group_by text[] default array['model_label','policy_hash'],
  p_since timestamptz default now() - interval '90 days',
  p_batch_id uuid default null,
  p_terminal_status text default null
) returns jsonb
```

按 `p_group_by` 分组返回每组的 `count`、`wall_ms` 的 p50/p95/max、各归因桶的中位数、失败率、`terminal_error_code` 分布、`unattributed_pct`。允许的分组维度限定为白名单（`model_label`、`policy_hash`、`profile_config_hash`、`harness_version`、`capability_contract_hash`、`worker_id`、`batch_id`、`finished_at::date`），避免任意列注入。

```sql
-- 3) 预计算异常清单。让 AI 不必先捞 50 万条事件才能找到线索。
get_analysis_runtime_findings(
  p_batch_id uuid default null,
  p_since timestamptz default now() - interval '7 days'
) returns jsonb
```

每条 finding 形如 `{ code, severity, agent_run_id, evidence: {...} }`，code 取自固定枚举：

| code | 判据 |
|---|---|
| `HIGH_UNATTRIBUTED_TIME` | `unattributed_ms / wall_ms > 0.4` |
| `LOW_PARALLELISM` | `agent_count > 1` 且 `model_ms_sum / model_ms_union < 1.2` |
| `AGENT_IDLE_DOMINANT` | `agent_idle_ms / wall_ms > 0.3` |
| `RETRY_STORM` | `model_requests_by_kind->>'retry'` 占比 > 20% |
| `COMPACTION_HEAVY` | `compaction` 占比 > 15% |
| `TOOL_DOMINATED_BY_ONE` | 单个工具占 `tool_ms_sum` > 50% |
| `AGENT_NO_EVIDENCE` | 某 Agent `model_requests > 5` 且 `evidence_produced = 0` |
| `SUBMIT_CONTENTION` | `rejected_submissions > 0` |
| `UNCLOSED_AT_END` | `open_at_end` 非空 |
| `EVENTS_DROPPED` | `events_dropped > 0` |
| `SLOW_REGRESSION` | 同指纹分组内 p95 比前一周期恶化 > 30% |

这张表同时是 §13 告警的数据源，人和 AI 用同一套判据，避免两边结论不一致。

## 7. Worker 接入设计

### 7.1 新增 Worker 事件客户端

建议新增：

```text
worker/src/monitoring/runtime-event-types.ts     事件契约（discriminated union）
worker/src/monitoring/runtime-event-reporter.ts  有界队列 + 定时 flush + 折叠
```

Reporter 要求：

- 每个事件先生成 `event_uuid`，再入队；重试复用同一 UUID。
- **必须有基于时间的 flush，不能只按条数。** flush 触发条件取三者之一：队列达到 64 条、距上次 flush 达到 `RUNTIME_EVENT_FLUSH_MS`（默认 800ms）、或调用 `flush()`。只按条数 flush 会重现 `analysis_tool_audit` 的问题——“正在调用”永远来不及被看见。
- 单 Attempt 内存队列上限 512。溢出时按 §7.3 的优先级丢弃，并记录 `runtime_event_dropped`（只记数量与 event_type）。
- 单次 flush 走一个 `report_analysis_runtime_event_batch` RPC，硬超时 10 秒（与 §6.1.3 的 30 秒逃生阀留足余量）。
- 失败采用有界退避重试（例如 200ms / 600ms / 1800ms，共 3 次），仍失败则整批丢弃并计数。仓库现有 Broker 审计的“unshift 回队首、无退避”不要照抄。
- 保持每个 `correlation_id` 生命周期内的相对顺序：同一 correlation 的 STARTED 必须与 TERMINAL 在同一批，或 STARTED 在更早的批。
- `close()` 尽力 flush 一次，但不得无限阻塞 Attempt 收敛。
- 不捕获任意对象作为 payload；TypeScript 按 event type 定义严格字段，禁止 `Record<string, unknown>` 直通。
- 监控失败不能放宽权限、预算、root-only、证据或 lease 校验。

### 7.2 关键约束：不新增 Broker 路由（阻塞级决策）

`scripts/v4-harness-manifest.mjs:48` 把 `brokerRoutes` 纳入 `semanticManifest`，因此**新增一条 Broker 路由会改变 manifest 哈希**。而：

- `0031` 的 `freeze_v4_job_manifest_and_policy_hash` 触发器把活动 manifest 的 `manifest_hash` 冻结到 `analysis_job.capability_contract_hash`，`enforce_analysis_job_policy_immutable` 保证它冻结后不可变。
- `worker/src/ai/runtime/factory.ts:105-112` 在 `input.task.capability_contract_hash !== currentContractHash` 时抛 `SESSION_FORMAT_UNSUPPORTED`。

连起来的后果是：**新增路由 = 新 Worker 拒绝执行任何在途 Job 的任务**，部署必须先排空所有活动批次。

但 `semanticManifest` 只哈希 `brokerRoutes` 的「路由 → `{capability, mutating}`」映射，**完全不涉及请求体形状**。因此：

> V1.5 的全部实时插桩通过**扩展现有路由的请求体**实现，不新增路由、不新增 `modelTools`、不改 `v4-capability-contract.json`。

复用映射：

| 用途 | 复用路由 | 现有 capability | payload 新增字段 |
|---|---|---|---|
| 工具生命周期 | `/attempt/tool-audit` | `usageReport` | `lifecycle: { phase, correlationId, toolName, occurredAt, durationMs?, errorCode? }` |
| 模型请求开始 | `/attempt/reserve-model-request` | `usageReport` | `correlationId`（Broker 在 verdict 通过时自行产生 STARTED） |
| 模型请求终态 | `/attempt/report-usage` | `usageReport` | `correlationId`、`phase`、`durationMs`、`failed` |

三条路由都已在契约里、都是 `usageReport` capability，且 `/attempt/tool-audit` 已被 `toolNameIsSubject` 判定为“toolName 是被审计对象而非调用意图”（`attempt-control-broker.ts:443`），所以扩展它不会放宽任何权限。

Phase 3 的 Workflow/Job 实例树确实需要新路由，因此它**必须**配一个 manifest 迁移（`0033`）并安排排空窗口。这是 Phase 3 独立于首版的根本原因。

### 7.3 工具生命周期：`tools/pre-execute`（核心）

插桩点：`worker/src/harness-plugins/agent-authority-policy/index.ts:231`，已经是 `ctx.on('tools/pre-execute', ..., { global: true, prepend: true })`。它对**每一个 Agent 的每一次工具调用**都会触发，并且已经解析出了 `identity`（`agentId` / `sessionId` / `role` / `agentCapability` / `tools`）。

这是覆盖全部 30 个模型工具的唯一插桩点。`worker/src/ai/acp/acp-client.ts:285` 的 `onToolCall` 只消费 root session 的 `session/update`，子 Agent 的会话通知不在其中，因此**不能**作为多 Agent 场景的数据源，只保留为漂移交叉校验（见 §7.7）。

改造方式（在现有 hook 内包住 `next()`，不新增 hook，保证与角色判定同一条代码路径）：

```text
tools/pre-execute:
  identity = await registry.resolve(...)           // 现有逻辑，失败仍然 deny
  correlationId = randomUUID()

  if (!identity.tools.includes(toolName)):
    post(TOOL_CALL_DENIED, correlationId)          // 复用现有 reportDenial，加 lifecycle 字段
    return deny                                    // 现有行为不变

  startedPost = post(TOOL_CALL_STARTED, correlationId)   // 不 await，避免给每次工具调用加延迟
  t0 = now()
  try:
    return await next()
  catch (err):
    chain(startedPost, () => post(TOOL_CALL_FAILED, correlationId, now()-t0, stableCode(err)))
    throw
  finally:
    // 成功路径
    chain(startedPost, () => post(TOOL_CALL_COMPLETED, correlationId, now()-t0))
```

`chain(startedPost, ...)` 表示把 TERMINAL 的 POST 挂在 STARTED 的 POST settle 之后。这样既不给工具调用增加同步延迟，又保证同一 correlation 的两条上报不会在 Unix socket 上乱序（Node 的 http agent 可能用不同连接，纯 fire-and-forget 会乱序）。

`DELEGATION_TOOLS` 的 `beginDelegation` / `endDelegation` 现有逻辑保持不动，位置不变。

#### 事件量控制：1 秒折叠（阻塞级补充）

大多数工具（`read` / `grep` / `glob` / `read_snapshot_code`）在毫秒级返回。为它们各写两行事件是纯浪费。

**折叠规则（在 Worker 侧的 Reporter 里实现，不在插件里）：**

- STARTED 入队时不立即视为最终形态，打上 `pendingCollapse`。
- 如果同 correlation 的 TERMINAL 在**同一个 flush 周期内**到达，把两条折叠成一条 TERMINAL 事件，带 `duration_ms` 与 `payload.collapsed = true`，STARTED 不落库。
- 如果 flush 时 TERMINAL 还没到（即工具已经跑了 ≥ 一个 flush 周期，约 800ms），STARTED 照常落库；TERMINAL 后到时作为独立事件落库。

效果与代价：

- 事件量从「每工具 2 行」降到「快工具 1 行 + 慢工具 2 行」，按常见分布可省 60%~80%。
- **代价（必须写进 UI 说明）**：800ms 内完成的工具不会出现「正在调用」态，只会出现在已完成历史里。这恰好是人类监控台真正关心的语义——“卡住的工具”，而不是“闪过的工具”。
- 折叠不改变审计：`analysis_tool_audit` 仍然按原逻辑记录每次调用。

队列溢出时的丢弃优先级（从先丢到后丢）：已折叠的快工具 TERMINAL → `MODEL_REQUEST_COMPLETED` → `TOOL_CALL_*` STARTED。**`*_DENIED` / `*_FAILED` / 任何 ATTEMPT/AGENT/JOB scope 事件永不丢弃**，宁可挤掉高频工具事件。

#### Broker 侧改造

`attempt-control-broker.ts` 的 `ingestAudit`（`:717`）扩展为：识别请求体里的 `lifecycle` 字段，转投 `options.reportRuntimeEvent?.(...)`；`entries` 数组的现有审计行为完全不变。

新增 `AttemptControlBrokerOptions.reportRuntimeEvent`，由引擎接到 Reporter，与现有 `flushAudit` / `saveArtifact` / `markAgentTerminal` 同一模式。

**必须同时修正 usage 计数污染：** `handle()`（`:493` 附近）目前对**每一个** Broker 请求都执行 `toolCalls++` 与 `toolCallsByName[bucket]++`，而 `toolCalls` 最终会经 `commit_analysis_agent_usage` 落成 `analysis_agent_run.tool_calls`。现在 `/attempt/tool-audit` 只在被拒时被调用，污染很小；接入生命周期上报后每次工具调用会多出 2 次请求，`tool_calls` 会被放大 2~3 倍。

修正：在 `handle()` 里把纯观测路由（`/attempt/tool-audit`、`/attempt/report-usage`）从 `toolCalls` / `toolCallsByAgent` / `toolCallsByName` 的累加中排除。这同时修掉了一个已存在的小幅虚高。

### 7.4 为什么必须走插件而不是 Broker dispatch

`v4-capability-contract.json` 的 `modelTools` 共 30 项，其中 `origin: "platform"` 只有 5 个（`search_snapshot_code`、`find_snapshot_files`、`read_snapshot_code`、`list_snapshot_commits`、`submit_review_result`）。其余 25 个是 `origin: "harness"`：`skill`、`todo_write`、`create_goal`、`update_goal`、`get_goal`、`ralph`、`subagent`、`subagent_fork`、`send_message`、`interrupt_agent`、`list_agents`、`workflow`、`job_list`、`job_output`、`job_kill`、`bash`、`read`、`read_image`、`write`、`edit`、`grep`、`glob`、`web_search`、`web_fetch`、`exit_plan_mode`。

Harness origin 的工具在 Harness 进程内执行，**根本不经过 Broker**。如果只在 Broker dispatch 前插桩，监控台的「正在调用工具」只能看到那 5 个平台工具——而实现型 Agent 的绝大部分时间花在 `bash` / `edit` / `read` 上。

`tools/pre-execute` 是唯一同时满足下列条件的边界：进程内、覆盖全部工具、已有 Agent 身份、已有 fail-closed 语义。

### 7.5 模型请求生命周期

真实 provider 边界只有一个：`worker/src/harness-plugins/usage-reporter/index.ts` 的 `ctx.on('llm/stream', ..., { global: true, prepend: true })` 内的 `metered()` 生成器。文件头注释已说明它是 Harness 里每一次流式模型调用的唯一入口（agent-loop 轮次、`dsh-llm-retry` 重发、自动压缩、会话标题都经过它）。

初版方案里“provider adapter 未接入，只能显示 reserved”的降级**不需要**了。三个精确位置：

1. `identity` 解析失败 → 现有 `denialChunk('AGENT_IDENTITY_INVALID')` 之前，上报 `MODEL_REQUEST_DENIED`（`error_code = 'AGENT_IDENTITY_INVALID'`）。
2. `verdict?.allowed !== true` → 现有 `denialChunk` 之前，上报 `MODEL_REQUEST_DENIED`（`error_code = verdict.code`）。**provider 确实没有被联系**，这一点由“不调用 `next()`”保证。
3. `verdict.allowed === true` 且在 `for await (const chunk of next())` **之前** → `MODEL_REQUEST_STARTED`。
4. `finally` 块内 → `MODEL_REQUEST_COMPLETED`（带累加的 `inputTokens` / `outputTokens`，可为 null）或 `MODEL_REQUEST_FAILED`（`failed === true` 时）。

必须改动的现有行为：`finally` 里的上报目前被 `if (inputTokens !== null || outputTokens !== null)` 包住，provider 不报 token 时**完全不发** `/attempt/report-usage`。要改成无条件上报生命周期终态，token 字段保持 null。这是让「模型请求已结束」可见的前提。

`correlationId` 在 `metered()` 开头生成一次，四个位置共用。`model_request_kind` 直接用现有 `RequestClassifier.classify()` 的结果，不另立分类。

`MODEL_REQUEST_STARTED` 也可以由 Broker 在 `reserveModelRequest` 返回 allowed 时产生（Worker 进程内，更省一次往返），但那样拿不到 `finally` 的终态配对。**决策：STARTED 与 TERMINAL 都由插件产生**，保持同一 correlation 由同一方生成，避免两侧各生成一半导致配不上。

其中 `verifyPins` / `broker` / `recordProfile` / `registerAgentNode` / `resolveResume` / `runTurn` 是明确的 `await` 边界；`sessionSlot` / `workspace` / `materializeAttemptProfile` / `startProcess` 是同步调用，只报完成。

禁止只在日志调用旁复制事件而不确认边界。例如 `agent_attempt_started` 日志（`engine:423`）出现在 `registerAgentNode` **之后**，可以据此报 `ROOT_AGENT_REGISTERED`；但不能把日志位置当成边界去猜。

### 7.7 交叉校验与降级

- `acp-client.ts` 的 `onToolCall`（引擎已接为 `agentToolCalls[name]++`）与插件上报的工具数做比对。若 `agentToolCalls` 有某工具而生命周期事件里没有，记 `runtime_event_tool_drift`（含工具名与差值），说明插件 hook 漏了或上报被丢。**不用它补数据**，只用它发现问题。
- Broker 不可达时插件的上报会失败。现有 `usage-reporter` 对预算是 fail closed（拒绝调用 provider），但**监控上报失败必须 fail open**：只写 stderr，不影响工具执行与模型调用。
- Reporter 关闭或 feature flag 关闭时，Broker 的 `reportRuntimeEvent` 为 undefined，插件的 lifecycle 字段被静默忽略，现有审计行为不变。
- 数据库侧 `revoke execute` 停写时，Worker 会每批报错。Reporter 必须识别 `42501 / insufficient_privilege` 并**自动进入静默模式**（停止上报、每 5 分钟记一次日志），不能持续刷错误日志。

### 7.8 Workflow / Harness Job 协议（Phase 3）

### 8.3 刷新策略

首版：

- 活动批次事件增量：每 2.5 秒调用 `get_analysis_runtime_console(batch, cursor)`。
- 完整快照：每 12 秒以 `cursor=null` 校准。

- 按 `event_uuid` 去重（不是按 id），与 §6.1.3 的水位裁剪配合。

数据新鲜度分三档，且**三种故障分别展示，不合并**：

| 状态 | 判据 | 含义 |
|---|---|---|
| 实时 | `server_time - received_at < 5s` | 正常 |
| 延迟 | 5–15s | 链路拥塞 |
| 陈旧 | `> 15s` 且任务 `agent_status='RUNNING'` | 明显告警 |
| 确认延迟 | `watermark_lag_ms > 3000` | 有长事务未提交，事件已到但未过水位 |
| Worker 离线 | heartbeat 超过 20 秒（与 `reclaim_stale_story_task_leases` 的窗口一致） | Worker 侧问题 |

### 8.5 AI 取数通道：只读诊断 CLI

AI Agent 没有浏览器，也不应该为了取数去到处连生产库。需要一个仓库内的只读脚本。

```text

```

```bash
# 单次 attempt 完整诊断（最常用）
node scripts/runtime-report.mjs attempt --task <task_id> [--attempt N] [--format md|json]

# 跨运行趋势 / 回归对比

# 预计算异常清单

```

设计约束（这些是硬要求，不是建议）：

- **只读。** 脚本只调用 §6.10 的三个查询 RPC，不执行任何 DDL/DML。代码里不出现 `insert` / `update` / `delete` / `drop`。
- **凭据不落盘、不回显。** 从环境变量或既有 `.env.local` / `.docker/worker.env` 读取，**绝不打印**，输出前对结果做一次与 §10.4 同源的敏感模式扫描，命中则拒绝输出并报错。
- **`--format md` 默认。** Markdown 表格 + 归因摘要，便于 AI 直接阅读，也便于人贴进 issue。`--format json` 给程序化处理。
- **输出必须自带可信度。** 开头固定打印 `instrumentation_health`（`events_dropped`、`unattributed_pct`、`timeline_truncated`），让 AI 先知道这份数据能不能采信，再看结论。
- **默认连本地。** 无显式 `--remote` 时连本地 Supabase；连生产需要显式加 `--remote` 并二次确认，避免误查。
- 与 `npm run lint` 的 `oxlint src worker supabase scripts` 覆盖范围一致，新脚本自动纳入 lint。

建议同时加 npm 脚本：

```json

"monitor:findings": "node scripts/runtime-report.mjs findings"
```

## 10. 测试与验收

### 10.1 数据库（`supabase/tests/0032_..._test.sql`）

按仓库约定：`\set ON_ERROR_STOP on`、单个 `BEGIN ... ROLLBACK`、独立固定 UUID 命名空间、`pg_temp.assert*`、输出唯一成功标记。

- 幂等：同一个 `event_uuid` 重试 10 次只产生一行，返回同一个 id，投影只更新一次。
- Task fencing：错误 worker、错误 claim token、错误 attempt、过期 lease 的事件全部拒绝。
- Job fencing：非持有者 Worker 的 `JOB_*` 事件被拒；`FINALIZING` 阶段校验 `finalizer_worker_id` 与 lease。
- Lineage：Agent 事件不能关联到其他 run/node；未解析到 node 的事件被丢弃并计数，不使整批失败。
- Projection：乱序重试不能把 current activity 回退到旧事件；不同 correlation 的 TERMINAL 不覆盖新活动。
- **投影清理**：`save_agent_review_result` / `fail_agent_review` / `reclaim_stale_story_task_leases` 之后，该 run 下所有 node 的 `current_activity_*` 运行态被清空，且未闭合 correlation 被补写 `TOOL_CALL_CANCELLED`。
- **游标水位**：模拟两个并发事务（后取号者先提交），断言未提交事务的事件不被返回，且 `next_event_id` 不越过它；提交后两条按 id 顺序返回，无跳号。
- 权限：ADMIN 与批次创建者 REVIEWER 可读；非创建者 REVIEWER 与 VIEWER 被拒；`anon` 全拒绝；`insert_analysis_runtime_event` 对所有角色不可执行。
- 终态原子性：业务终态与终态事件同时提交或同时回滚。
- Payload allowlist：提交含 `prompt` / `command` / `api_key` / 绝对路径的 payload，断言落库后这些键不存在。
- Retention：`purge_analysis_runtime_events` 不清理活动 Job 的事件；按 `p_limit` 限量；返回删除行数；**清理后 `analysis_agent_run_rollup` 行数不变**。
- `event_day` 确定性：同一 `event_uuid` 重试（含 `clock_skewed` 被钳制的情况）落到同一个 `event_day`。
- 汇总正确性：构造一个已知事件序列（含两个 Agent 的重叠工具区间），断言 `tool_ms_sum > tool_ms_union`、`busy_ms_union <= wall_ms`、`setup + busy + teardown + unattributed = wall_ms`。
- 汇总容错：`compute_analysis_run_rollup` 抛错时业务终态仍提交，且该 run 的 `rollup_version = 0` 可被 `backfill_analysis_run_rollups` 补算。
- 汇总幂等：重复计算同一 run 只有一行，`computed_at` 更新。
- `get_analysis_run_trend` 的 `p_group_by` 传入白名单外的列名时报错，不拼进 SQL。
- `get_analysis_attempt_diagnostics` 在事件超过 5000 条时返回 `timeline_truncated = true`，不静默截断。

### 10.6 事件量实测（Phase 0 必做）

初版方案假设「批次累计 10,000 条事件」。接入全工具后这个数字很可能低一个数量级，必须用生产数据校准，而不是估算。

测算步骤：

```sql
-- 1. 每次 attempt 的实际工具调用数分布
select
  agent_run_id,
  count(*) as tool_calls,
  count(*) filter (where duration_ms >= 800) as slow_calls
from public.analysis_tool_audit
group by agent_run_id
order by tool_calls desc
limit 50;

-- 2. 每次 attempt 的模型请求数
select agent_attempt, model_requests, agent_count
from public.analysis_agent_run
where status in ('COMMITTED', 'FAILED')
order by model_requests desc
limit 50;
```

按 §7.3 折叠规则推算单批次事件量：

```text
事件数 ≈ 需求数 × (
    Attempt 阶段事件 ~12
  + Agent 注册/终态 × 2 × Agent 数
  + 工具事件：快工具 × 1 + 慢工具 × 2
  + 模型事件：模型请求数 × 2
)
+ Job 层事件 ~10
```

判定门槛：

- 单批次 > 200,000 或单日 > 1,000,000 → `0032` 直接建按 `received_at` 的月分区。
- `analysis_tool_audit` 里 `duration_ms >= 800` 的比例 > 40% → 说明折叠收益低，需要考虑把 `RUNTIME_EVENT_FLUSH_MS` 调大，或对特定高频只读工具只记 TERMINAL。

判定门槛修正：由于 §6.1.1 已决定「不分区 + 预留 `event_day`」，这个数字**不再阻塞 Phase 1**。它现在只决定两件事：

1. **什么时候**切分区（单日 > 100 万条，或表接近 5000 万行时另开 contract migration）。
2. 折叠窗口是否要调大（`duration_ms >= 800` 占比 > 40% 说明折叠收益低）。

因此这一步可以与 Phase 1 并行，或在 Phase 2 首个 Worker 上线后用真实事件量直接测得。产出的数字写回本节。

## 11. 部署顺序

必须采用 expand-first：

1. 备份数据库并记录当前迁移版本与 active Harness manifest（`v4_harness_manifest` 表的 `is_active` 行）。
2. 在测试环境顺序应用到 `0032`，执行 §10.1 的 SQL 测试。
3. 用**旧 Worker**跑一个小批次，证明 expand migration 向后兼容（旧 Worker 不上报事件，业务不受影响）。
4. 构建新 Worker：`npm run worker:build`（内含 `harness:manifest:check`），确认 manifest 哈希**未变**。
5. 先滚动部署 1 个新 Worker，跑单需求 smoke，核对：事件链路、node 投影、`open_correlations`、`tool_calls` 未虚高、敏感字段扫描。
6. 滚动部署其余 Worker，观察事件写入延迟、Reporter 队列深度、dropped 计数、`watermark_lag_ms`。
7. 部署前端 `/monitoring`，先仅 ADMIN 使用。
8. 执行权限、断线恢复、多 Agent 并发和失败路径验收。
9. 稳定后再进入 Phase 3——它需要独立的 manifest 迁移与排空窗口。Phase 5 同样独立灰度。

Worker 容器命令（与仓库现状一致）：

```bash
docker compose -f docker-compose.worker.yml build worker
docker compose -f docker-compose.worker.yml up -d --scale worker=4
```

数据库迁移在部署窗口由明确负责人执行 `supabase db push` 或团队正式迁移流程。仓库当前没有生产自动迁移流水线，不能假设部署前端/Worker 会自动应用 SQL。

## 12. 回滚方案

### 12.1 前端回滚

回退到无 `/monitoring` 的前端版本。数据库与新 Worker 可继续写事件，不影响原页面。不删除事件表。

### 12.2 Worker 回滚

三级，优先用最轻的：

1. `RUNTIME_EVENTS_ENABLED=false` 滚动重启——保留新 Worker 的其他修复，只停止事件产生。
2. 回退到旧 Worker 镜像——业务分析继续使用现有表/RPC。
3. 页面看到 `last_event_at` 陈旧后显示“监控数据已暂停”，**不得把任务判定为失败**。

旧 Worker 必须在 `0032` expand schema 上保持兼容。注意：只要没改 `v4-capability-contract.json`，新旧 Worker 的 manifest 哈希相同，可以混跑同一批次——这是 §7.2 决策带来的关键回滚自由度。

### 12.3 数据库回滚

不优先执行 destructive down migration（仓库没有 down migration 惯例）。推荐顺序：

1. 回退前端。
2. `RUNTIME_EVENTS_ENABLED=false` 或回退 Worker。
3. `revoke execute on function report_analysis_runtime_event_batch from service_role` 停写（Worker 按 §7.7 自动静默）。
4. 保留新增列和事件表，待问题修复后继续使用。
5. 只有确认无任何新 Worker/前端依赖后，另开 contract migration 删除对象。

Realtime 回滚只需从 publication 移除表并回退前端订阅；cursor polling 必须仍可工作。

## 13. 可观测性与运维

仓库**没有 metrics 系统**（`session-telemetry-otel` 在契约 `disabledPlugins` 里被显式禁用，全仓无 prometheus/statsd/OTel）。首版不新建 metrics 出口。

替代方案：结构化日志字段 + SQL 聚合。这也是 AI 侧的第二条通道（§1.2）——数据库是主，日志是独立备份。

### 13.1 Attempt 归因摘要日志（AI 的备份通道）

每次 attempt 终态时，**除了写汇总表，再落一行自包含的结构化日志**。这行日志的价值在于它不依赖数据库汇总成功：`compute_analysis_run_rollup` 失败、事件被清理、甚至数据库短暂不可用时，日志里仍然有这次运行的完整归因。AI 在只能拿到日志的场景下（例如查一个 30 天前已被清理的 run）仍可分析。

```json
{
  "event": "attempt_rollup",
  "level": "info",
  "agent_run_id": "...", "task_id": "...", "batch_id": "...", "agent_attempt": 3,
  "terminal_status": "COMMITTED", "terminal_error_code": null, "end_reason": null,
  "model_label": "...", "policy_hash": "...", "profile_config_hash": "...",
  "harness_version": "...", "capability_contract_hash": "...",
  "wall_ms": 2418000, "setup_ms": 12400, "model_ms_union": 1580000,
  "tool_ms_union": 402000, "busy_ms_union": 1902000, "teardown_ms": 8100,
  "agent_idle_ms": 210000, "unattributed_ms": 495500,
  "model_ms_sum": 2740000, "tool_ms_sum": 610000,
  "agent_count": 6, "max_concurrent_agents": 3, "max_concurrent_tools": 4,
  "model_requests": 84, "model_requests_by_kind": {"loop": 71, "retry": 9, "compaction": 4},
  "tool_calls": 512, "tool_calls_denied": 3, "tool_calls_failed": 11,
  "tool_ms_by_name": {"bash": 210000, "read": 61000, "grep": 44000},
  "input_tokens": 1840000, "output_tokens": 96000,
  "evidence_count": 27, "rejected_submissions": 0,
  "events_reported": 1104, "events_dropped": 0,
  "unattributed_pct": 20.5, "rollup_version": 1
}
```

要求：

- 字段名与 `analysis_agent_run_rollup` 的列名**逐字一致**，这样 AI 用同一套字段名既能查库也能读日志，不需要两套映射。
- 一行 JSON，不换行，便于 `grep`/`jq` 提取。`per_agent` 数组不进日志（体积太大），只进汇总表。
- 走 `logger.ts` 的 `redact()`，同样不含路径、命令、凭据。
- 这行日志**不能**替代汇总表：日志有轮转和保留上限，长期趋势仍以汇总表为准。

Worker 侧其余日志（经 `worker/src/logger.ts`，沿用 `event: '<同名>'` 约定）：

| 日志事件 | 字段 |
|---|---|
| `runtime_event_flushed` | `count`、`duration_ms`、`duplicated`、`dropped_unresolved_agent` |
| `runtime_event_flush_failed` | `count`、`attempt`、`error_code` |
| `runtime_event_dropped` | `count`、`event_type`、`queue_depth` |
| `runtime_event_queue_high` | `queue_depth`（超过上限 80% 时） |
| `runtime_event_collapsed` | `count`（每次 flush 折叠掉的对数） |
| `runtime_event_tool_drift` | `tool_name`、`observed`、`reported` |
| `runtime_event_silenced` | `reason`（进入静默模式时） |

数据库侧聚合（可做成 ADMIN 只读 RPC，或运维手工查询）：

```text
runtime_console_stale_active_tasks   RUNNING 任务中最近事件超过 15 秒的数量
runtime_event_receive_lag_p95        received_at - occurred_at 的 p95
runtime_event_watermark_lag          最老未过水位事件的滞后
runtime_event_open_correlations      未闭合超过 5 分钟的 correlation 数
runtime_event_table_rows             表行数与最早 received_at
```

告警建议：

- 活动 task 超过 15 秒没有事件且 heartbeat 在线：事件链路异常。
- heartbeat 离线且 task lease 仍有效：Worker/lease 异常。
- `runtime_event_dropped` > 0：立即告警。
- `runtime_event_silenced`：立即告警（说明权限被回收或配置异常）。
- p95 receive lag > 5 秒持续 5 分钟：数据库或网络拥塞。
- `watermark_lag` > 30 秒：存在长事务，游标逃生阀已生效。
- 未闭合 correlation 超过 5 分钟且 run 已终态：说明 §6.2 规则 5 的清理有漏洞。
- 事件表增长超过 §10.6 测算的容量预算，或 retention 清理连续失败：运维告警。

## 16. 最终实施决策

0. 监控系统服务**两类消费者**：人（当下、增量、中文）与 AI（历史、自包含、机器码）。两者共用同一份事实事件流，但取数接口、保留策略和聚合层分开设计。数据库与 RPC 永不返回展示文案。
0.1 **AI 侧的载体是数据库 + 日志，不是前端界面。** 三处落点：`analysis_runtime_event`（细节，30 天）、`analysis_agent_run_rollup`（归因基线，长期）、`attempt_rollup` 结构化日志（独立备份通道，字段名与汇总表逐字一致）。诊断 RPC 只授予 `service_role`/ADMIN，不进浏览器攻击面。前端只服务人的实时监控。
1. Attempt 继续使用 `analysis_agent_run`，不新增重复业务表。
2. 新增 `analysis_runtime_event` 作为唯一浏览器实时事实流，带 `xact_id` 提交水位。
3. **游标必须按 `pg_snapshot_xmin` 水位裁剪**，并配 30 秒逃生阀；前端按 `event_uuid` 去重。
4. 高频投影只写 `analysis_agent_node`；`analysis_agent_run` 只存 ATTEMPT 阶段；run 级当前活动查询时聚合，不落列，不制造热行。
5. `current_activity_event_id` / `attempt_phase_event_id` 用裸 bigint，不加外键，避免互相引用与清理写放大。
6. **首版不改 `v4-capability-contract.json`**：全部实时插桩通过扩展 `/attempt/tool-audit`、`/attempt/reserve-model-request`、`/attempt/report-usage` 的请求体实现。这避免了 `factory.ts:105` 造成的排空窗口，也保留了新旧 Worker 混跑的回滚自由度。
7. **工具生命周期插桩在 `agent-authority-policy` 的 `tools/pre-execute`**，这是覆盖全部 30 个模型工具的唯一边界；`acp-client.ts` 的 `onToolCall` 只做漂移交叉校验。
8. **模型生命周期插桩在 `usage-reporter` 的 `metered()`**，STARTED 与 TERMINAL 由同一方生成；必须去掉 token 为 null 就不上报的现有短路。
9. Reporter 必须有 ≤1 秒的定时 flush，并用同 flush 周期折叠快工具，把事件量压到可运营区间；折叠代价（<800ms 的工具没有“正在调用”态）明确写进 UI 说明。
10. 工具实时生命周期与完成后 audit 并存，互不冒充；`analysis_tool_audit` 逻辑不动。
11. 观测路由必须从 Broker 的 `toolCalls` 计数中排除，否则 `analysis_agent_run.tool_calls` 会被放大。
12. Attempt 终态、Agent 终态、租约回收必须在同一事务清投影并补写未闭合 correlation 的 CANCELLED。
13. 收敛路径的事件不得依赖 claim token（提交后 claim 已被清空），一律在终态 SQL 内写或用 `session_revision` fencing。
14. Job 层事件按 `analysis_job.worker_id` / `finalizer_worker_id` + lease 做 fencing，不套用 task 四要素。
15. `/monitoring` 仅 ADMIN；批次控制台用 `ensure_manage_review_batch`，**不用** `ensure_view_review_batch`（它只校验角色不校验归属）；`can_view_review_batch` 的越权问题单独记为待修项。
16. `cost_micros` 不接入，DTO 与 UI 均不出现。
16.1 **`0032` 不建分区**（分区表的唯一约束必须含分区键，会打断 `event_uuid` 幂等，已实测），但加入 `event_day` 列——由钳制后的 `occurred_at` 确定性推导，让将来切分区成为机械操作而非重新设计。
16.2 **新增 `analysis_agent_run_rollup`，长期保留、不随事件清理。** 原始事件 30 天就清，跨月的「优化前后对比」只能靠它。汇总计算失败不回滚业务终态，走 `rollup_version = 0` 标记 + 异步补算。
16.3 **定义显式的墙钟时间归因模型**（§6.9.2），`sum` 与 `union` 并存以体现并行度，并保留 `unattributed_ms` 桶度量插桩盲区——它允许为大值，但**禁止摊平到其它桶**假装归因完整。
16.4 **为 AI 单独提供三个诊断 RPC**（单 attempt 自包含诊断、跨运行趋势、预计算异常清单），不让 AI 走游标增量接口。趋势 RPC 的分组维度走白名单。
16.5 **提供只读诊断 CLI `scripts/runtime-report.mjs`** 作为 AI 的取数通道：只读、凭据不回显、输出前做敏感扫描、默认连本地、输出自带 `instrumentation_health` 可信度标注。
16.6 payload 白名单新增六个诊断字段（`exit_code`、`output_bytes`、`truncated`、`hit_count`、`line_span`、`retry_index`），判定标准是「不能反推出源码或凭据」；命令文本、输出正文、文件路径仍然禁止。
17. 所有事件 payload 执行严格 allowlist，由数据库函数重建，禁止原始内容和凭据。
18. Workflow/Harness Job 没有真实协议前明确不可展开；Phase 3 需要独立 manifest 迁移与排空窗口。
19. 不新建 metrics 系统；可观测性落在结构化日志字段与 SQL 聚合上。
20. 推荐首版交付 Phase 0 → 1 → 2 → 4，之后再做 Phase 3 和 Phase 5。

按此方案实施后：

- **人看到的**是 Worker 与 Harness 真正执行过、并被数据库接受的运行节点——包括每个 Agent 当前正在跑的那条 `bash` 或那次模型请求——而不是前端根据日志、计数或延迟审计推测出的动画状态。
- **AI 拿到的**是一份可归因、可跨版本比对、并且**自带可信度标注**的运行档案：一条命令就能取回「这次 attempt 40 分钟花在哪、哪个 Agent 空转、和上周同指纹的运行比慢了多少、以及这份数据本身有多少时间是我们还没插桩到的」。

两者共用同一份事实，不会出现「界面说正常、分析说有问题」的分歧1111。
