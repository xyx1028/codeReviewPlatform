# 代码评审平台 V1.5 真实运行监控台指标图文说明

> 适合第一次使用这个页面的人。本文不讲数据库和代码实现，重点解释：页面上的数字是什么、怎么看任务是否正常、卡住时先查哪里。

## 一句话说明

这个页面不是给 AI 打分的，而是一个**运行过程监控台**，主要回答三件事：

1. 当前有多少需求正在执行、等待、成功或失败。
2. 某条需求执行到哪一步，由哪个 Worker 和哪些 Agent 处理。
3. 如果任务卡住，卡在模型请求、工具调用还是 Worker 上。

页面的层级关系是：

```text
运行批次
  └─ 需求任务
       └─ Attempt  第几次执行尝试
            └─ Agent Tree  根 Agent 和子 Agent
                 └─ 运行时间线  后台真实发生的事件
```

## 一 从刚开始运行的页面看懂核心数字

![批次刚开始运行时的监控页面](<./images/runtime-monitoring-start.png>)

这张图表示批次刚进入分析阶段，最重要的是下面这些数字。

| 页面显示 | 白话解释 | 本图表示什么 |
|---|---|---|
| 活动批次 `1` | 当前有 1 个批次还没有结束 | 正在执行 `test01` |
| 运行中 / 等待需求 `8 / 18` | 8 条正在执行，18 条还没开始 | `8 + 18 = 26`，正好是本批次全部需求 |
| 成功 / 失败需求 `0 / 0` | 还没有需求成功，也没有需求失败 | 26 条都处于运行中或等待中 |
| 在线 Worker / 占用槽位 `4 · 8/8` | 4 个 Worker 在线，8 个槽位已占用，总槽位也是 8 | 当前并发容量已经用满，新需求需要等待 |
| 需求进度 `0/26` | 成功需求数 / 总需求数 | 目前成功 0 条，总共 26 条 |
| 最近事件 `14 秒前` | 最近一条后台事实事件是什么时候发生的 | 用来判断监控数据是否及时 |
| 游标 `#704` | 页面已经安全读取到第 704 号事件 | 用于补拉时间线，不是业务进度 |

### `4 · 8/8` 不是小数 4.8

正确拆法是：

```text
4 · 8/8
│   │ └─ 总槽位 8
│   └─── 已占用槽位 8
└─────── 在线 Worker 4 个
```

因此，这张图表示 **4 个 Worker 一共提供 8 个并发槽位，而且 8 个槽位都在忙**。

### `0/26` 不代表系统没动

进度条的分子只统计**成功结束的需求**。此时虽然显示 `0/26`，但已经有 8 条需求正在运行。

## 二 执行过程中进度怎样变化

![批次执行到 11 个成功需求时的监控页面](<./images/runtime-monitoring-progress.png>)

这张图中，批次进度已经变成：

```text
成功 11 + 运行中 8 + 等待 7 + 失败 0 = 总数 26
```

因此 `11/26` 的准确含义是：**26 条需求里已有 11 条成功提交分析结果**。

需要注意：

- 失败任务不会被加到进度条分子里。
- 如果成功 11、失败 2，总数 26，进度仍显示 `11/26`，同时在下面单独显示“失败 2”。
- 这样可以避免把失败任务误算成已完成成果。

左侧需求列表中出现：

- **成功**：这条需求的正式结论已经保存。
- **结论已提交**：对应 Attempt 已完成正式提交。
- **延迟**：只是说最近事件不够新，不代表需求失败。
- **未分配 Worker**：任务结束后已经释放 Worker，因此成功任务也可能显示未分配。

## 三 成功后的 Attempt 和 Agent 数据怎么看

![需求成功后显示 Attempt 用量和时间线的页面](<./images/runtime-monitoring-success.png>)

### 批次进度 `13/26`

这张图中的完整关系是：

```text
成功 13 + 运行中 8 + 等待 5 + 失败 0 = 总数 26
```

### `已提交` 和 `已完成` 的区别

| 页面位置 | 状态 | 含义 |
|---|---|---|
| 需求任务 | 成功 / 结论已提交 | 这条需求已经保存正式分析结论 |
| Attempt | 已提交 | 这一次执行尝试完成了正式提交，不是单纯停止运行 |
| 根评审 Agent | 已完成 | 这个 Agent 节点已经结束工作 |

三者是不同层级的状态，并不重复：

```text
Agent 已完成
    ↓
Attempt 完成正式提交
    ↓
需求任务变成成功
```

### 模型请求 `45`

表示这一次 Attempt 累计发起了 45 次模型请求，可能包含：

- 正常 Agent 轮次
- 请求重试
- 上下文压缩
- 会话标题等辅助请求

请求次数是**工作量和资源用量**，不是质量分数。次数多不一定更好，次数少也不一定更差。

### 工具调用 `141`

表示本次 Attempt 累计调用了 141 次工具，例如：

- `bash`
- `grep`
- `edit`
- 平台提供的业务工具

工具调用数同样不是质量分数，需要结合最终结论、证据和错误情况判断。

### Token `2,379,692 / 16,589`

斜杠左右分别表示：

```text
累计输入 Token / 累计输出 Token
```

这里表示：

- 累计输入 Token：`2,379,692`
- 累计输出 Token：`16,589`

输入 Token 很大不一定异常。因为一次 Attempt 可能包含很多轮模型请求，每一轮都可能重复携带历史上下文，所以输入 Token 会累计得很快。

### 为什么 Attempt 显示工具调用 141，Agent 卡片却显示工具 0

因为两处口径不同：

| 区域 | 数据口径 |
|---|---|
| Attempt 顶部 | 整次 run 的总账 |
| 单个 Agent 卡片 | 某一个 Agent node 的分账 |

总账有 141 次调用，而节点显示 0，表示工具调用已经记入整次 Attempt，但没有全部归因或回填到这个 Agent 节点。

因此：

- 看整次任务消耗，以 Attempt 顶部为准。
- 排查某个 Agent 做过什么，结合 Agent 卡片和运行时间线。
- Agent 显示 `Token 未上报`，不能理解成 Token 消耗为 0。

## 四 运行批次每一列是什么意思

| 列名 | 含义 |
|---|---|
| 批次 | 批次名称；下一行是周次代码和目标分支，例如 `20260909 · release` |
| 分析任务状态 | 排队中、准备代码、分析中、汇总结果、已完成或失败 |
| 需求进度 | 成功需求数 / 总需求数；下方另外显示运行中、等待和失败数 |
| 运行时长 | 从批次任务开始到当前服务端时间 |
| 最后活动 | 最近一条运行事实距离现在多久 |
| 事件号 | 最近事件的技术编号，方便开发排查 |
| 数据新鲜度 | 监控数据是否及时，不是 AI 分析质量分数 |
| 查看 | 将下面的需求、Agent Tree 和时间线切换到这个批次 |

### 批次状态

| 状态 | 含义 |
|---|---|
| 排队中 | 批次已经创建，等待开始 |
| 准备代码 | 正在准备仓库和固定代码版本 |
| 分析中 | Worker 正在处理需求 |
| 汇总结果 | 需求处理接近完成，正在收敛批次结果 |
| 已完成 | 批次成功结束 |
| 失败 | 批次级流程失败，需要查看错误信息 |

## 五 左侧需求任务列表怎么看

| 字段 | 含义 | 常见判断 |
|---|---|---|
| 需求编号和名称 | 当前被分析的业务需求 | 可以使用顶部搜索框筛选 |
| 等待 / 运行中 / 成功 / 失败 | 需求级状态 | 这里只认需求的 `agent_status` |
| 重试 N | 已经进入第 N 次 Attempt | 大于 1 说明之前失败、被接管或恢复后重开 |
| 当前活动 | 最新 Attempt 或最新运行中 Agent 的真实活动 | 例如尝试启动中、正在请求模型、正在调用工具 |
| 活动持续时间 | 当前活动已经持续多久 | 异常长时结合未闭合调用和新鲜度判断 |
| Worker | 当前领取任务的 Worker 标识 | 未分配表示还没领取，或者任务结束后已释放 |
| Agent N | 当前仍处于运行状态的 Agent 数量 | 不是本次一共创建过的 Agent 数量 |
| 深度 N | Agent 委派树达到的最大深度 | 根 Agent 是 0，直接子 Agent 是 1 |
| 几秒前 | 该需求最近一次事件时间 | 和新鲜度一起判断任务是否仍在活动 |
| 错误文案 | 稳定错误码翻译后的中文 | 失败时先看这里，再看完整时间线 |

### 等待和卡住不是一回事

- **等待**：任务还没有被 Worker 领取，常见原因是所有槽位都在忙。
- **运行中且持续有新事件**：通常只是任务正在正常执行。
- **运行中但超过 15 秒没有事件**：页面会标为“陈旧”，需要检查事件链路或 Worker。
- **存在未闭合调用**：模型请求或工具调用有开始事件但没有结束事件，这是最直接的卡点证据。

## 六 Attempt 与 Agent Tree 指标

### Attempt 是什么

Attempt 可以理解为：**这条需求的一次完整执行尝试**。

同一条需求第一次执行失败、Worker 租约被接管或会话需要恢复时，可能出现后续 Attempt。页面默认展示最新一次，也可以切换回历史 Attempt 查看为什么重试。

| 指标 | 含义 |
|---|---|
| 第 N 次 | 当前查看的 Attempt 序号 |
| 运行中 / 已提交 / 失败 | Attempt 的整体状态 |
| 阶段 | Attempt 当前真实阶段，例如尝试启动中、模型编排中、正在收敛 |
| 已持续 | 当前阶段已经持续多久，阶段切换后重新计时 |
| Agent N | 本次 Attempt 已经登记的 Agent 总数 |
| 最大深度 | Agent 委派树达到的最大层级 |
| 恢复 N 次 | 同一会话被恢复继续执行的次数，不是新建了 N 个 Attempt |
| 模型请求 | 本次 Attempt 累计模型请求数 |
| 工具调用 | 本次 Attempt 累计工具调用数 |
| Token 输入 / 输出 | 模型提供方上报的累计 Token；未上报和 0 是两回事 |

### 单个 Agent 卡片

| 字段 | 含义 |
|---|---|
| 根评审 / 检索 / 实现 / 批判 / 工作流 | Agent 的职责角色 |
| 根 / 派生 / 分叉 / 工作流 / Ralph 循环 | Agent 是怎样产生的 |
| 深度 | 当前 Agent 位于委派树第几层 |
| 模型请求 / 工具调用 / 证据 | 这个 Agent 节点累计完成的活动数 |
| 当前活动 | 这个 Agent 此刻正在做什么 |
| 未闭合的调用 | 已经开始但还没有结束的模型或工具调用，是排查卡点的首要位置 |
| 错误码 | 这个 Agent 的稳定失败原因中文解释 |

### 当前能力范围

当前版本还没有接入：

- Harness Job 实例树
- Workflow 内部步骤明细

页面只会显示已经接入的 `job_*` 或 `workflow` 工具活动，不会虚构步骤和完成百分比。

## 七 运行时间线怎么看

时间线是这个页面最接近“证据”的部分。它展示后台实际接受的事实事件，不根据耗时或工具名称猜测状态。

| 字段或开关 | 含义 |
|---|---|
| Attempt 分组 | 将同一次执行尝试的事件放在一起 |
| 模型 N | 当前分组识别出的模型请求数量 |
| 工具 N | 当前分组识别出的工具调用数量 |
| N 条事实 | 当前分组包含的原始事件数量 |
| 耗时 | 开始事件和结束事件之间的持续时间 |
| 事件作用域 | 批次、需求、Attempt、Agent、模型、工具、Workflow 或 Harness Job |
| 进行中 | 事件已经开始，但还没有闭合 |
| 仅异常 | 只显示失败、拒绝、取消或带错误码的事件 |
| 技术码 | 展开事件编号、事件类型、活动码和关联 ID，供开发排查 |
| 时钟偏差 | Worker 上报时间超出允许范围，服务端保留事件并标记偏差 |
| 加载更早事件 | 当前需求事件过多时继续加载更早记录 |

### 精简视图和完整日志

- **精简视图**：合并重复事件，以及成对的开始和结束事件，适合快速了解过程。
- **完整日志**：保留更细的事件记录，适合排查问题。

### 为什么有些工具只有“完成”，没有“正在调用”

不足 800 毫秒就结束的工具不会显示短暂的“正在调用”，而是直接出现在已完成历史中。

这是刻意设计：监控台主要关注可能卡住的长调用，不追逐一闪而过的短调用。

## 八 数据新鲜度五种状态

| 状态 | 判定标准 | 代表什么 | 建议动作 |
|---|---|---|---|
| 🟢 实时 | 最近事件少于 5 秒 | 监控数据正常跟上 | 无需处理 |
| 🟠 延迟 | 最近事件 5 到 15 秒 | 可能有轻微链路延迟 | 先观察是否恢复 |
| 🔴 陈旧 | 任务仍在运行，且超过 15 秒没有事件 | 运行状态与事件链路可能不同步 | 查看 Worker 心跳和未闭合调用 |
| 🟡 确认延迟 | `watermark_lag_ms > 3000` | 事件已到数据库，但有长事务未提交，游标暂时不能越过 | 检查数据库长事务，等待提交 |
| 🔥 Worker 离线 | 运行中任务心跳超过 20 秒 | Worker 进程可能掉线或卡死 | 检查 Worker 进程和容器 |

注意：

- “陈旧”不等于 AI 已经失败。
- “延迟”不等于 Worker 已经离线。
- 成功任务旁边也可能暂时出现“延迟”，因为任务已经结束，不会继续产生新事件。

## 九 遇到问题时按这个顺序排查

1. **看在线 Worker 和占用槽位。** 没有在线 Worker 就先处理 Worker；槽位全满时，等待需求暂时不启动是正常的。
2. **看数据新鲜度。** 实时说明页面可信；确认延迟查数据库长事务；Worker 离线查进程或容器。
3. **点选具体需求。** 确认它是等待、运行中、成功还是失败，并查看 Worker、最近事件和错误文案。
4. **打开最新 Attempt。** 查看阶段、持续时间、Agent 数和未闭合调用。
5. **查看完整日志并打开技术码。** 将事件号、错误码、Attempt 和 Worker 标识交给开发或运维。

## 十 最容易误解的三个点

### 1. `0/26` 不是系统没动

它只表示还没有需求成功结束，同时可能已经有 8 条需求正在运行。

### 2. 两处 `Agent 1` 口径不同

- Attempt 区域的 `Agent 1`：本次 Attempt 已登记的 Agent 总数。
- 左侧需求卡片的 `Agent 1`：当前仍在运行的 Agent 数量。

### 3. 请求数和 Token 不是质量分数

模型请求数、工具调用数和 Token 是工作量与资源用量。请求多不代表分析一定更好，请求少也不代表分析一定更差。
