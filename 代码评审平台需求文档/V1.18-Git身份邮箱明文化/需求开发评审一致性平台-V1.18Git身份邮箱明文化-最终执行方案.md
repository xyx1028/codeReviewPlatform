# 需求开发评审一致性平台 V1.18：Git 身份邮箱明文化最终执行方案

## 1. 背景与目标

Git 身份原本只存 HMAC 指纹 + `x***@domain` 掩码，明文既不落库也不回显。这在内部平台上
是纯负担：

- 列表看不出这一行是谁的邮箱。同首字母 + 同域名的人并排出现，线上实测 `j***@kingdee.com`
  同时是 `jin_gu` 和 `junjie_xiang` 两行；
- 管理员改一个作者别名也得把整个邮箱重打一遍，打错还会多出一行身份；
- 明文其实早就在库里：`git_identity_email_candidate.email_plain` 存着反查出来的候选邮箱，
  并且已经通过 `get_my_git_email_discovery` 返回给本人。掩码只拦住了管理员自己。

目标：邮箱在身份表里存明文、在页面直接显示、编辑时回显；归属匹配继续只认指纹。

## 2. 范围与非目标

包含：`developer_git_identity` 新增明文列、历史行回填、三条写入路径都带明文、两个读取
RPC 暴露明文、管理员页与个人中心显示明文并回显编辑。

非目标：

- **不动 `email_fingerprint`**。它是归属匹配（`match_analysis_git_identities`）与
  `analysis_job_identity_snapshot` 的键，改它等于让历史分析结论失去可追溯性；
- **不动提交侧**。`analysis_repository_commit.author_email_masked` 仍是掩码：它属于冻结
  清单，参与 manifest 规范化与哈希，改动要连 Worker 契约一起走，另开一版再说；
- 不改 RLS：`developer_git_identity` 仍然只能通过 definer 函数读写（表上 RLS 开启且无策略），
  管理员列表照旧先过 `ensure_admin()`。

## 3. 验收标准

1. 明文列只接受规范化后的邮箱（小写、单个 `@`、长度 ≤320），否则 CHECK 拒绝；
2. 历史行能从反查候选按指纹回填；回填不到的行界面回落掩码并提示"保存一次即补全"；
3. 管理员代录把当场输入的明文落库并回传；
4. 自助绑定（本人认领候选）无需改动函数就能带上明文；
5. `admin_list_developer_git_identities` 与 `get_my_git_identity` 返回 `author_email`；
6. 明文列不进任何索引或唯一约束——唯一性与匹配仍由指纹负责；
7. 迁移可重复应用。

## 4. 设计

| 关注点 | 做法 |
|---|---|
| 存储 | `developer_git_identity.author_email text`，CHECK 校验格式且要求 `= lower(...)` |
| 历史行 | 迁移内 `update ... from (select distinct on (email_fingerprint) ...)` 从候选表回填 |
| 自助路径 | `before insert or update of email_fingerprint, author_email` 触发器：调用方没给明文时按指纹从候选表补。两个长函数（`upsert_my_git_identity_from_candidate` / `_from_email`）因此**一行未改**，发布窗口内新旧前端混用也不会有行为差 |
| 管理员路径 | `admin_upsert_developer_git_identity_from_email` 里 upsert 之后显式 `update ... set author_email=v_email`，并在返回值里带上 `author_email` |
| 显示 | 前端优先 `author_email`，为空回落 `masked_email` 并注明是旧记录 |

掩码列保留：审计行引用它，回填不到明文的行也还要靠它显示。

## 5. 实施步骤与文件范围

1. `supabase/migrations/20260923085908_git_identity_plaintext_email.sql`：加列 + 约束 + 回填 +
   触发器 `fill_git_identity_author_email()` + 三个函数 `create or replace`（管理员代录、
   管理员列表、`get_my_git_identity`）+ 更新那条说"明文永不存储"的函数注释；
2. `supabase/tests/20260923085908_git_identity_plaintext_email_test.sql`：同名 SQL 测试；
3. `src/types.ts`：`DeveloperGitIdentityRecord.author_email`、`MyGitIdentityRecord.author_email`，
   并修正两处已经不成立的注释；
4. `src/lib/api.ts`：保存返回值类型带上 `author_email`；
5. `src/pages/GitIdentityManagementPage.tsx`：列表列显示明文、编辑回显、顶部说明改写；
6. `src/pages/ProfilePage.tsx`：个人中心列表与"不可修改"标题同样优先明文；
7. `src/lib/__tests__/v111-api-adapters.test.ts`：明文 + 历史行为 null 两条用例。

## 6. 安全与回滚

- 明文可见范围没有扩大到平台之外：管理员列表仍过 `ensure_admin()`，本人只读自己的行，
  表本身不可直连。内部平台、公司邮箱本身公开，这是本次明确接受的取舍；
- 日志与 Worker 侧未新增明文输出（Worker 读的是指纹）；
- 回滚：写一个新的前进迁移 `alter table ... drop column author_email`（掩码与指纹都还在，
  界面回落掩码即可），Worker 无需改动。
