# 需求开发评审一致性平台 V1.17：本地全链路排查修复最终执行方案

## 1. 背景与目标

在本地 Supabase + 4 个本地 Worker 上把一个真实批次（26 个需求、四仓 1482 条冻结提交、
模型 glm5.3-flash 经宿主机代理）**完整跑通**，逐层核对准备 → 冻结 → 归属 → Agent 执行 →
提交 → 汇总 → 监控，把过程中暴露的缺陷全部修掉。

首轮 26 需求任务的结果是 `SUCCEEDED 26/26`，链路本身是通的；但取证过程暴露了 6 个缺陷，
其中 2 个会让任务整体失败、3 个让监控与审计失真、1 个让本地诊断链路完全不可用。

## 2. 范围与非目标

包含：

- 诊断 CLI 的本地默认连库；
- 运行监控工具名词表补齐 V1.11 的四个 Story 提交工具（数据库 + Worker + 漂移守卫）；
- Broker 错误码不再把稳定码抹成 `TOOL_FAILED`，并对真正分不出类的失败补日志；
- 范围扩展在"已达目标层级"时改为成功空操作；
- 证据类型在 Worker 侧校验（此前只有数据库 CHECK 兜底）+ 提示词写明合法取值；
- `max_tokens` 截断改为有界续写，不再让一个需求的超长输出把整个 Job 判失败；
- 增量基线（上次成功 Job 的 head）只许放宽分析范围、不许收窄，并在四仓范围全空时留日志。

非目标：

- 不改归属算法（V1.16 已单独处理）；
- 不改 AI 裁定门禁语义（`ANALYSIS_SCOPE_TRIAGE_INCOMPLETE` 仍然是硬门禁）；
- 不动云端环境：全部在本地库与本地 Worker 上验证，发布由用户手动执行。

## 3. 缺陷清单与根因

| # | 现象 | 根因 | 影响 |
|---|---|---|---|
| 1 | `npm run monitor:attempt` 默认模式直接报"SUPABASE_URL 不是本地地址" | `resolveCredentials` 两种模式都并入 `.docker/worker.env`（云端），再被自己的本地守卫拒掉 | 任何跑过云端 Worker 的机器上，本地诊断链路等于不存在 |
| 2 | 723 条 `TOOL_CALL_COMPLETED` 里 33 条没有 `tool_name`；`tool_calls_by_name` 出现 `unknown` | `analysis_runtime_known_tool_names()` 缺 V1.11 的 4 个工具；`analysis_runtime_event_payload()` 对不在词表里的值**静默丢弃** | V1.11 最核心的四个工具在监控里无名；平台/Harness 侧耗时归因把它们算错边 |
| 3 | 审计里 8 条 `TOOL_FAILED`（submit/verdict） | Broker catch 只认 `SnapshotError`，`DbError` 与前缀式普通 Error 的稳定码被丢弃 | "模型没读 diff 就下判定"与"工具崩了"在审计与监控里长得一样 |
| 4 | 5 条 `SCOPE_EXPANSION_INVALID` 拒绝 | 范围已是 GLOBAL 时任何扩展请求都抛硬错 | 降级任务里 Agent 必然撞错，白烧轮次并污染拒绝计数 |
| 5 | 4~5 次提交失败：`violates check constraint "analysis_agent_evidence_evidence_type_check"` | Worker 侧**完全不校验** `evidenceType`；提示词也没写合法取值 | 模型自造类型 → 数据库原始约束报文 → 靠猜重试；重试都错则 attempt 失败 → fail-fast 拖垮整个 Job |
| 6 | 4 需求任务 `FAILED`（2 个已提交）：`AGENT_TURN_INCOMPLETE / max_tokens` | 输出被单次上限截断即判终态失败 | 评审结论本就是长文本，一个需求截断就让整批失败 |
| 7 | 线上批次 test3 的任务四仓 `base == head`、Commit 数 0、26/26 `NO_CANDIDATE` 全仓降级 | `fetchHistory` 只要确认"上次成功 Job 的 head 是本次 head 的祖先"就采用它做 base；git 认为一个提交是自己的祖先，两个 Job 冻结在同一个 head 时范围就是空集 | **第一个成功的 V2 Job 会废掉同分支上后续每个 Job 的精准提交分析**，直到仓库来新提交；范围为空还会让全部需求退化成全仓评审（更贵、更差） |

### 缺陷 7 详解（本轮追加，影响面最大）

线上同一个批次、同一份代码，两个任务的差别：

| Job | 范围 | scope 分布 |
|---|---|---|
| `9b87185f`（03:54，范围正常） | 四仓 `TIME_DERIVED`，1482 条提交 | 14 `DEVELOPER_WINDOW` + 3 `DEVELOPER_WINDOW/WEAK_CANDIDATES_CAPPED` + 1 `HYBRID_CANDIDATES` + 7 `NO_CANDIDATE` + 1 `NO_STRONG_SCOPE`，候选合计 **511** |
| `5e4b0f67`（07:50，命中本缺陷） | 四仓 `PREVIOUS_SUCCESSFUL_JOB`，`base==head`，0 条提交 | **26 × `GLOBAL_FALLBACK/NO_CANDIDATE`，候选合计 0** |

修正规则：`base` 取 {上次成功 head, 时间窗基线} 里**更老的那个**。时间窗（`enqueue` 时声明，
默认 21 天）是这一批要求覆盖的最小面，必须始终被覆盖；上次成功 head 只在它更老时生效
（那时它补上的是"距上次分析已超过窗口"的提交，确实不该漏）。新增稳定回落原因
`PREVIOUS_BASE_INSIDE_WINDOW`，它只出现在清单 JSON 与日志里，不涉及数据库列与约束。

另外补一条 warn 日志 `analysis_range_empty_all_repositories`：四仓范围全空时提前喊一声，
不再只是范围卡片上一排安静的 0。

## 4. 需求与验收标准

1. 本地默认模式下三条 `monitor:*` 命令可直接查本地库；显式远端地址而不加 `--remote` 仍必须拒绝；
2. 冻结契约里的每个模型工具、Broker 每条平台工具路由名都在数据库词表里；平台工具集合在
   数据库 / Worker 归因 / Broker 路由三处一致；运行事件不再出现无名工具、rollup 不再出现 `unknown`；
3. 数据库与内部门禁的稳定错误码原样出现在响应与审计里；真正分不出类的失败留一行
   `broker_tool_failed_unclassified` 日志；
4. 已达或超过目标层级的扩展请求返回 `expanded: false` 的成功响应，不记新的扩展事实、层级不变；
   非法目标层级仍然 422；
5. 非法 `evidenceType` 在 Worker 侧就以 `EVIDENCE_TYPE_INVALID` 拒绝并列出合法取值；提示词写明三个取值；
6. `max_tokens` 截断有界续写（默认 2 次），取消时不续写，其它 stop reason 不续写；续写写日志；
7. 上次成功 head 等于本次 head、或落在时间窗内部时，范围必须回落到时间窗基线（`range_source=TIME_DERIVED`、
   `range_fallback_reason=PREVIOUS_BASE_INSIDE_WINDOW`）；它比时间窗基线更老时仍然生效；四仓全空时有 warn 日志。

## 5. 总体设计与关键取舍

- **词表只增不放宽**：`analysis_runtime_event_payload()` 丢弃未登记 `tool_name` 的行为**保留**
  （防止任意文案透传），补的是词表本身，并用漂移守卫把"契约 ⊆ 词表"钉住；
- **稳定码优先，`TOOL_FAILED` 只兜底**：先 `SnapshotError.code`，再 `err.code`（`DbError`），
  再消息前缀 `^([A-Z][A-Z0-9_]{2,63}):`，都没有才 `TOOL_FAILED` 且必须留日志；
- **空操作不是错误**：扩展到已达层级返回成功但 `expanded: false`，单调性靠"不记事实、不改层级"保住，
  不靠抛错；
- **截断续写有上界且照常计量**：每次续写都经 `usage-reporter` 的预算门禁，`maxTruncatedContinuations=0`
  可完全恢复旧行为。

## 8. 安全、兼容与回滚

- 两个 SQL 函数是 `immutable` 纯函数，只增词条，可重复应用；不改表结构、不改 RLS；
- 词表校验语义未放宽：任意文案（`rm -rf /`、`unknown`）仍被丢弃，有 SQL 测试断言；
- 证据类型校验是**收紧**：此前能通过 Worker 的非法类型本来也会被数据库拒绝，所以不会让原本
  能提交的结论失败，只是把拒绝点前移并给出可读原因；
- 截断续写会额外消耗模型请求，但每次都过预算门禁；`maxTruncatedContinuations=0` 即回滚该行为；
- 回滚：迁移用新的前进迁移覆盖回旧定义；Worker 侧还原文件并重建镜像，无数据变更。
