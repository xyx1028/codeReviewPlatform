## 三、配置身份 HMAC Pepper（必做）

Git 身份匹配需要 Supabase Vault 中存在下面这个 Secret：

```text
analysis_identity_pepper
```

推荐操作：

1. 在你自己的终端生成随机值：

   ```bash
   openssl rand -hex 32
   ```

2. 打开目标 Supabase Dashboard 的 **Vault / Secrets**；
3. 新建 Secret，名称填写 `analysis_identity_pepper`；
4. Value 粘贴刚生成的随机值；
5. 保存后不要把 Value 截图、发给别人或写进 migration。

只检查名称和时间，不读取 Secret 内容：

```sql
select name, created_at
from vault.decrypted_secrets
where name = 'analysis_identity_pepper'
order by created_at desc;
```

- [ ] 至少存在一条同名 Secret；
- [ ] 不要随意轮换。轮换后，原有 Git 身份 fingerprint 会失效，必须在“Git 身份”页面重新保存所有邮箱。

## 四、配置 GitLab MR API（可选）

不配置也能使用 Commit/Diff 核心功能；页面会显示：

```text
MR_METADATA_UNAVAILABLE
```

这表示“没有读取 MR 元数据”，**不表示没有 MR**。

如需读取 MR 标题、Description、作者、分支、Commit 集、merge/squash SHA：

1. 在企业 GitLab 创建独立只读 Access Token；
2. Token 必须能读取四个白名单仓库的 API，通常需要 `read_api`；以企业 GitLab 实际提供的 scope 为准；
3. 不要复用 `GITLAB_DEPLOY_TOKEN`；
4. 编辑真实配置文件：

   ```text
   /Users/kingdee/codeReviewPlatform/.docker/worker.env
   ```

5. 填写：

   ```text
   GITLAB_API_TOKEN=<你的只读Token>
   ```

- [ ] Token 没有写进 `.docker/worker.env.example`；
- [ ] Token 没有出现在 Git、截图、聊天或普通日志中；
- [ ] Token 对四仓都有读取权限，否则对应仓会显示 `PARTIAL/FAILED`，核心 Git 分析仍继续。

## 七、配置开发人员 Git 身份（必做，至少先配灰度人员）

1. 登录平台管理员账号；
2. 打开侧边栏 **Git 身份**；
3. 点击“新增 Git 身份”；
4. 填写：
   - 开发人员姓名：与需求 Excel 的开发人员文字一致；
   - 员工号：建议填写，用于区分同名；
   - Git author email：开发人员实际提交代码使用的邮箱；
   - Git 作者别名：例如英文名、Git 显示名；
   - GitLab 用户名/User ID：有则填写；
   - 人员状态、Git 身份状态：确认无误后选择“已验证”；
5. 保存后页面只应显示脱敏邮箱，例如 `d***@example.com`。

让开发人员在自己的仓库执行以下命令确认 author email：

```bash
git config user.email
```

一个人有多个 Git 邮箱时：找到该人员任意一行，点击 **新增邮箱**，每个邮箱建立一条身份记录。

- [ ] 没有在页面、数据库普通查询或日志中看到完整邮箱；
- [ ] 同一个邮箱不能绑定两个有效人员；
- [ ] 先配置参与灰度需求的开发人员即可，其他人员可以逐步补充；
- [ ] 未配置身份时，结构化 `Story-Id` 仍有效，但历史漏标召回会变弱。

## 九、创建灰度批次验收（必做）

建议先选择少量、提交记录清晰的需求。

1. 导入需求，需求编码使用真实完整编号；
2. 开发人员按《V1.11 开发提交填写规范》填写 Commit/MR；
3. 在“开始分析”页面选择：

   ```text
   V1.11 精准提交分析（推荐）
   历史漏标辅助窗口：21 天
   ```

4. 点击“开始 V1.11 精准分析”；
5. 在运行监控中观察状态：

   ```text
   QUEUED → PREPARING_CODE → PREPARING_SCOPE → PROCESSING → FINALIZING → SUCCEEDED
   ```

验收要求：

- [ ] 四仓都有冻结 `base → head`；
- [ ] 只有 `enumeration_status = COMPLETE` 才显示范围完整；
- [ ] 能看到强关联、AI 候选、选择原因和规则版本；
- [ ] AI 候选有真实 Diff 读取记录；
- [ ] AI 候选逐条得到 `RELATED / UNRELATED / UNCERTAIN`；
- [ ] 范围扩展只有 `PRIMARY → RELATED → GLOBAL`，并有原因；
- [ ] 最终实现证据来自冻结最终代码，不只引用 Diff；
- [ ] 页面和普通日志没有完整邮箱、Token、Diff 正文；
- [ ] 没配置 MR Token 时，`MR_METADATA_UNAVAILABLE` 不影响任务完成；
- [ ] 配置 MR Token 后，可以看到 MR 标题/描述/作者/分支/Commit 集增强信息；
- [ ] 再创建一个“兼容全仓 V1”小任务，确认旧流程仍能运行。

## 十、出现问题时发给我的信息

可以提供：

- `supabase migration list --linked` 输出；
- `supabase db push --linked --dry-run --skip-vault` 的报错；

- 哪个仓库、哪个阶段失败；

不要提供：

- `GITLAB_API_TOKEN`；
- `GITLAB_DEPLOY_TOKEN`；
- Supabase service role key；
- `analysis_identity_pepper` 的值；
- `.docker/worker.env` 全文；
- 开发人员完整邮箱或生产 Diff 正文。

## 十一、回滚方法

如果 V2 灰度异常：

1. 新任务在页面改选 **兼容全仓分析（V1）**；
2. 暂停继续创建 V1.11 任务；
3. 排空 V2 在途任务后，再回滚 Worker/前端代码；
4. 删除 `.docker/worker.env` 中的 `GITLAB_API_TOKEN` 可停止后续 MR API 采集；
5. 已创建的 V2 数据保留只读，用于排查；
6. 数据库不执行 down migration、不删除新表、不执行 reset；需要修复时继续新增前滚 migration。
