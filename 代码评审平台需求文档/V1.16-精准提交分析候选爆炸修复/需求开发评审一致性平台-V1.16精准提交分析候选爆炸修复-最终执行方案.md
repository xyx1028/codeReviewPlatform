# 需求开发评审一致性平台 V1.16：精准提交分析候选爆炸修复最终执行方案

## 1. 背景与目标

2026-09-23 线上（Job `61b35269`，26 个需求、四仓共 1482 条冻结提交）：**每一个**需求的分析范围
都是 `scope_error_code=STORY_CANDIDATE_LIMIT_EXCEEDED` + `scope_mode=GLOBAL_FALLBACK`、候选数 0，
Job 级 `scope_status=DEGRADED`。也就是说 V1.11「精准提交分析」在真实仓库上**完全没有生效**，
每个需求都退回全仓分析。

目标：让候选集合回到它的设计语义（与这个需求真正有关的提交），并且在超过上限时保留信息量
最高的证据，而不是把整条范围丢掉。

## 2. 范围与非目标

包含（全部在 Worker 侧，纯逻辑）：

- 弱信号判定不再包含恒真的「在冻结时间窗内」；
- 模块重合不再把需求项目名里的**仓库名**当模块线索；
- 候选超过上限时按优先级截断并记录降级原因，不再整条降级成全仓。

非目标：

- 不改数据库结构、RPC、上限值（200 仍是 `analysis_story_scope` 的硬约束）；
- 不改归属规则目录（13 条系统规则与 `ruleset_hash` 不变）；
- 不解决「需求负责人没有映射到已验证 Git 身份」这件事（本次 Job 26 个需求里有 8 个如此）——
  那是身份配置数据问题，靠 `/git-identities` 维护，不是代码问题。

## 3. 当前实现与问题

`worker/src/pipeline/story-scope.ts` 为每条提交构造归属输入时**硬编码** `withinFrozenWindow: true`
（提交清单本身就是按窗口枚举的，所以这个值恒真）。而
`worker/src/analysis/story-commit-attribution.ts` 把它算作弱信号：

```ts
const weakSignals = [identityStatus === 'WEAK_NAME', verifiedIdentity, input.withinFrozenWindow, input.moduleOverlap].filter(Boolean).length
if (weakSignals > 0 && identityStatus !== 'AMBIGUOUS') → WEAK_FALLBACK
```

于是窗口内**每一条**提交（只要身份不是 AMBIGUOUS）都拿到 WEAK 档 → `relevant.length ≈ 1482`
→ 越过 `> 200` 分支 → `globalScope(story, 'STORY_CANDIDATE_LIMIT_EXCEEDED')`。这对任何有 200 条
以上提交的窗口都必然发生。

第二个放大器：`moduleOverlap()` 把需求 `project_name` 切词后在提交文件路径里做子串匹配。线上
项目名形如 `kdmanage下架智能体提供租户影响范围（FT-2026-001591）`，切出 `kdmanage`；而这些仓库
的提交路径以仓库名开头（`kdmanage-backend/docs/...`），所以 `kdmanage` 命中该仓库每一条路径，
模块重合也退化成恒真。

第三个问题是降级方式本身：越过上限时整条 `GLOBAL_FALLBACK`，把**已经命中需求号的 STRONG 提交
一起扔掉**，换成"请看全仓"。这是信息量最低的处置。

## 4. 需求与验收标准

1. 窗口内、与需求无任何其它关系的提交不再成为候选（decision=GLOBAL_FALLBACK，tier 为空）；
2. 真正的弱信号（姓名别名匹配 / 已验证作者 / 模块重合）仍然产生 WEAK 候选；
3. 项目名里的仓库名不再让每条提交都算模块重合；
4. 候选超过 200 时：按 STRONG → AI_CANDIDATE → WEAK → CONFLICT → EXCLUDED（同级按分数）截断到 200，
   `scope_mode` 保持真实模式（不得变成 GLOBAL_FALLBACK），`status=DEGRADED`，
   `degradation_reasons` 含 `STORY_CANDIDATE_LIMIT_TRUNCATED`，manifest hash 按截断后的集合计算；
5. 数据库侧不出现 `STORY_CANDIDATE_LIMIT_EXCEEDED`（Worker 在发送前已截断到上限内）。

## 5. 总体设计

```text
提交清单（已按 21 天窗口枚举）
   → 每条提交 × 每个需求：attributeStoryCommit()
       弱信号 = {姓名别名, 已验证作者, 模块重合}    ← 去掉恒真的「在窗口内」
   → relevant = tier 非空的结果
   → sortStoryCandidates() 按 决策优先级 + 分数 排序
   → 超过 200 则截断（保留高优先级），记 STORY_CANDIDATE_LIMIT_TRUNCATED
   → createStoryCandidateManifest(截断后的集合) → 冻结
```

## 6. 数据与接口设计

- 数据库：**不涉及**（上限、约束、RPC 均不变）；
- 新增的稳定降级原因字符串 `STORY_CANDIDATE_LIMIT_TRUNCATED` 写入既有的
  `analysis_story_scope.degradation_reasons` / `scope_error_code`（text 列，无枚举约束）；
- 前端：**不涉及**（监控台「分析范围」直接展示后端给的原因码）。

## 7. 前端与 Worker/运行时改造

- `worker/src/analysis/story-commit-attribution.ts`：`weakSignals` 去掉 `withinFrozenWindow`；
- `worker/src/pipeline/story-scope.ts`：`moduleOverlap(story, entry, repository)` 过滤与仓库名重叠
  的词与纯数字词；超上限改为按 `sortStoryCandidates` 截断；新增 `CANDIDATE_LIMIT = 200` 常量并
  注明它与数据库硬约束一致。

## 8. 安全、兼容与回滚

- 归属结果**会变**（这正是目的）：已冻结的旧 Job 不受影响（scope 一经冻结即不可变），
  新 Job 才使用新逻辑；
- `ruleset_hash` / `attribution_algorithm_version` 不变 —— 本次改的是引擎对信号的解释，
  不是规则目录。若之后要把"算法行为变更"纳入身份，需要单独升 `ATTRIBUTION_ALGORITHM_VERSION`
  并处理兼容，本次刻意不做（会让所有在途 Job 的 scope 身份失配）；
- 回滚：还原这两个文件并重建 Worker 镜像即可，无数据库变更。

## 9. 实施步骤与文件范围

1. `worker/src/analysis/story-commit-attribution.ts`（弱信号）；
2. `worker/src/pipeline/story-scope.ts`（模块重合 + 截断 + 常量）；
3. `worker/src/__tests__/v116-story-scope-candidate-limit.test.ts`（新增回归，4 个用例）。
