# 新功能执行文档规则

本 Skill 是新功能开发的完成门槛，不是可选的写作建议。只要任务包含新功能，就必须创建或更新执行文档；缺少文档时不得声称任务完成。

## 1. 先判断是否触发

以下任一情况视为新功能，必须执行本 Skill：

- 新增用户可见能力、页面、入口、交互或业务流程；
- 新增或扩展 API、RPC、数据库表、字段、迁移或持久化行为；
- 新增 Worker、DeepSeek Harness、Agent、Skill、工具、插件、Broker 路由或模型调用行为；
- 新增配置项、权限规则、运行策略、监控能力或部署能力；
- 对现有功能增加新的输入、输出、状态、角色、模块适配或兼容范围；
- 用户明确称任务为“新功能”“新需求”“新增能力”“接入”或“重构并引入新行为”；
- 一个混合任务同时包含功能开发与 Bug/样式修改。

以下情况不触发，不要为它们单独创建执行文档：

- 普通 Bug 修复：只把现有行为恢复到已经定义的预期，不新增能力、接口、状态或数据结构；
- 纯样式修改：只调整颜色、字号、间距、布局、图标、响应式表现或其他 CSS/视觉效果，不改变业务行为；
- 文案、注释、格式化、依赖锁文件整理等不改变产品行为的维护工作。

不能仅根据任务标题判断。Bug 修复如果同时新增 API、数据库结构、配置能力或业务行为，仍按新功能处理；样式任务如果改变交互流程、权限或数据行为，也按新功能处理。无法明确归类时，优先按新功能处理并生成文档。

## 2. 文档目录

所有新功能执行文档必须放在工作区根目录下：

```text
需求开发评审一致性平台/
```

禁止继续使用旧目录名 `代码评审平台/`，也不要把正式执行方案放到仓库根目录、`docs/`、临时目录或代码模块内部。

每个新功能使用版本化目录：

```text
需求开发评审一致性平台/V<主版本>.<次版本>-<功能短名>/
```

例如：

```text
需求开发评审一致性平台/V1.7-技能管理/
```

确定版本时遵循：

1. 用户指定版本时使用用户给定版本；
2. 用户未指定时，扫描 `../../../代码评审平台需求文档/` 下已有的 `V<主版本>.<次版本>-*` 目录；
3. 沿用最高主版本并取下一个未使用的次版本；
4. 功能短名使用简短、可检索的中文或既有产品术语，不使用“新功能”“优化”等空泛名称；
5. 已有同一功能目录时更新原目录，不重复创建新版本目录。

## 3. 文档命名

正式执行文档命名为：

```text
需求开发评审一致性平台-<版本><功能短名>-最终执行方案.md
```

例如：

```text
需求开发评审一致性平台/V1.7-技能管理/需求开发评审一致性平台-V1.7技能管理-最终执行方案.md
```

如果目标版本目录中已经存在 `*-最终执行方案.md`，优先更新该文件，不创建“新版”“最终版2”“修订版”等重复文件。

图文说明、验证指南等属于可选补充文件，不能替代最终执行方案。补充文件沿用现有命名形式：

```text
需求开发评审一致性平台-<版本><功能短名>-图文说明.md
需求开发评审一致性平台-<版本><功能短名>-验证指南.md
```

## 4. 创建和更新时机

1. 在理解现有代码和确定方案后、修改功能实现代码前，先创建执行文档骨架；
2. 文档必须描述准备实际实施的方案，不能只复制用户需求；
3. 实现期间发生数据模型、接口、流程、安全边界或文件范围变化时，同步更新文档；
4. 完成实现和验证后，将计划描述改成实际落地结果，记录真实修改范围和验证结果；
5. 最终回复必须给出执行文档路径；文档不存在或仍与实现不一致时，不得宣称新功能完成。

## 5. 最终执行方案的必要内容

文档应按功能复杂度保持简洁，但必须覆盖以下事实：

```markdown
# 需求开发评审一致性平台 <版本>：<功能名>最终执行方案

## 1. 背景与目标
- 为什么做
- 完成后提供什么能力

## 2. 范围与非目标
- 本次包含什么
- 明确不包含什么

## 3. 当前实现与问题
- 现有调用链、数据流或页面行为
- 当前缺口

## 4. 需求与验收标准
- 可验证的功能要求
- 边界与失败行为

## 5. 总体设计
- 组件职责
- 关键流程或 Mermaid 图

## 6. 数据与接口设计
- 数据库、类型、API/RPC、事件或配置变化
- 不涉及的项目应明确写“不涉及”

## 7. 前端与 Worker/运行时改造
- 页面与交互
- Worker、DSH、权限、预算、Session 或工具变化

## 8. 安全、兼容与回滚
- 权限、秘密、审计、旧数据和在途任务影响
- 上线与回滚方式

## 9. 实施步骤与文件范围
- 按依赖顺序列出实施步骤
- 列出主要新增/修改文件

## 10. 验证结果
- 实际运行的测试、类型检查、构建或烟测
- 未验证项与原因
```

不存在的子系统可以合并或标注“不涉及”，但不得删除背景目标、范围、验收标准、总体设计、实施步骤和验证结果。

## 6. 内容要求

- 结论必须以当前代码为依据，先调查再写方案；
- 使用真实文件路径、表名、RPC、组件和 Worker 模块名；
- 区分“计划实现”“已经实现”和“暂不实现”，完成后清理过时计划；
- Mermaid 图只表达关键数据流或时序，不堆砌无关节点；
- 不在文档中写 API Key、Token、密码、真实个人信息或完整敏感配置；
- 不伪造测试结果，没有运行的验证必须明确标注未运行；
- 文档与代码冲突时，以实际实现为准并立即修正文档。

## 7. 完成检查

新功能结束前逐项确认：

- 已在 `../../../代码评审平台需求文档/Vx.x-功能短名/` 创建或更新最终执行方案；
- 文件名使用新的产品名“需求开发评审一致性平台”；
- 文档描述与最终代码、数据库和运行流程一致；
- 验收标准可以逐条验证；
- 验证章节只记录真实执行结果；
- 最终回复中包含文档路径；
- 本次任务若属于普通 Bug 或纯样式修改，没有误创建无意义的版本文档。
